agent-orchestration

CLI surface: dadaia orchestrate {list|show|run|status|resume} · Closure: sdd-release-lifecycle-v1

Propósito

Executa workflows (DAGs de stages) onde cada stage dispatcha um agente especialista em um runtime escolhido (cli, Claude API, Codex, OpenCode). Suporta dependências entre stages, paralelização via parallel_group, gates de aprovação humana (operator-approval), binding de inputs (workflow inputs + stage outputs → próximas stages) e retomada após falhas ou gates.

Cada run produz um manifest imutável e um event log em JSONL, permitindo auditoria completa do que foi disparado, com qual prompt, em qual ordem e com que resultado.

Fluxo de uso

  1. dadaia orchestrate list — lista os 11 workflows pré-instalados (spec-refinement, tdd-cycle, bug-fix-fastlane, cross-cutting-feature, architecture-review, onboarding-new-repo, security-patch, game-dev-cycle, game-bugfix, game-spec-definition, deploy-validation-only).
  2. dadaia orchestrate show spec-refinement — mostra o schema do workflow (inputs, stages com needs/parallel_group/gate, expected_output).
  3. dadaia orchestrate run spec-refinement --input topic=auth — cria run (id gerado), persiste manifest.json, emite RUN_STARTED, identifica stages prontas (sem dependências pendentes) e despacha-as.
  4. O StageRunner agrupa stages com o mesmo parallel_group e despacha simultaneamente via AgentDispatcher (cli/claude/codex/opencode). Cada stage recebe seu invocation.md em .dadaia/runs/<run_id>/<stage_id>/.
  5. Quando um stage termina, ele escreve seu output (HTML/markdown report) no caminho declarado em expected_output; o runner recalcula próximas stages prontas e despacha novamente.
  6. Em gates de aprovação ou falhas, o run pausa com status apropriado. dadaia orchestrate status <run_id> mostra o estado do DAG; resume <run_id> retoma após o operador resolver o gate.

Trigger típico

Quando o operador quer executar um pipeline multi-agente — refinement de spec, ciclo TDD, fastlane de bugfix, onboarding de novo repo. Também usado por hooks/cron schedules para tarefas recorrentes.

Diferencial

Sem este runner, multi-agent flows precisariam ser disparados manualmente um a um, sem paralelização e sem persistência de estado. Os parallel_groups permitem padrões como "1 discovery → 5 specialists paralelos → 1 synthesis" sem encadeamento artificial. Gates evitam que o pipeline corra solto em decisões críticas. O event log imutável é fonte de verdade auditável para reproduzir runs ou diagnosticar falhas.

Estado runtime tocado

  • .dadaia/runs/<run_id>/manifest.json — registro imutável do run
  • .dadaia/runs/<run_id>/events.jsonl — append-only log de eventos (RUN_STARTED, STAGE_DISPATCHED, STAGE_COMPLETED, GATE_AWAITING, RUN_COMPLETED, RUN_FAILED)
  • .dadaia/runs/<run_id>/<stage_id>/invocation.md — prompt da stage
  • Paths declarados em expected_output de cada stage (tipicamente reports HTML em .dadaia/reports/<context>/<agent>/<ts>-<type>.html)

Dependências

  • Depende de context-management (resolve context ativo para path templating).
  • Depende de public-asset-distribution (workflows instalados a partir de public/workflows/).
  • Os 11 workflows + agentes especialistas dispatch-ados vivem como assets canônicos versionados.
