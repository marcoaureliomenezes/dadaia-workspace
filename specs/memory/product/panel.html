panel

CLI surface: dadaia panel [--port 4999] [--no-open] [--bind 127.0.0.1] · Closure: panel-r5-v1 · 2026-05-19

Propósito

O Dadaia Workspace Panel é a superfície de controle local do workspace: uma single-page app servida em http://127.0.0.1:4999/ que torna o produto navegável em uma janela única, sem ler markdown nem rodar comandos. Tem cinco abas, na ordem em que o operador as encontra: Spec Context Projects (default, ex-"Memories"; cards dos contextos ativos linkando para memory HTML servida verbatim), Agents (cards canônicos com status badge + 3-stat row + skills chips + system prompt lazy-fetched + tier accent), Workflows (12 cards canônicos com detail view hash-routed exibindo DAG SVG server-rendered), Sessions (tabela ordenável com sessions live do runtime ativo + drawer detalhado + auto-refresh pausado em document.hidden), e Servers (registry de dev servers + sub-seção "Unregistered listeners" com badge LAN-exposed).

Um theme switcher no topbar oferece três paletas (Mint default, Sage, Warm) persistidas em localStorage["dadaia-panel-theme"], com pre-paint script que evita FOUC e regra focus-visible com double outline scoped ao Warm para satisfazer WCAG. Ao lado do theme switcher vive o runtime switcher (Claude / Codex toggle) que pivota Agents, Workflows e Sessions simultaneamente para o runtime escolhido — global, não per-tab — via window.Runtime + localStorage["dadaia-panel-runtime"] + dadaia:runtime-change CustomEvent. As três paletas são axe-clean nas tabs Agents e Workflows (zero violações serious/critical). Hash routing segue gramática #<tab>[?key=val] — exemplo: #workflows?detail=tdd-cycle abre detail view e dispara GET /api/workflows/tdd-cycle; #agents?filter=<name> mantém compatibilidade do cross-link de workflow chips. O DAG é renderizado server-side em SVG via algoritmo longest-path layout — sem Mermaid no browser, sem JS de layout, com role="img" + <title> + per-node aria-label. Stdlib-only no runtime; Bearer token via secrets.token_urlsafe(32) em ~/.dadaia/state/panel.token (chmod 600); CSP + nosniff em todas as respostas; bind loopback-only.

Fluxo de uso

  1. Boot: operador roda dadaia panel a partir da raiz do workspace. Comando bind 127.0.0.1:4999 via ThreadingHTTPServer (stdlib), imprime Panel running at http://127.0.0.1:4999/, chama webbrowser.open() a menos que --no-open, e bloqueia até SIGINT. Pre-paint script lê localStorage["dadaia-panel-theme"] e seta data-theme=<mint|sage|warm> antes do first contentful paint — zero FOUC.
  2. Index: GET / renderiza HTML com 5 sections + topbar com theme switcher e runtime switcher. Default-active tab é Spec Context Projects; ordem de abas: Spec Context Projects → Agents → Workflows → Sessions → Servers. Tab switching client-side via panel.js com role="tablist" + role="tab" + role="tabpanel" + keyboard nav (ArrowLeft/ArrowRight cycle, Home/End jump, Enter/Space activate). Em viewport < 768px o label visível abrevia para "Spec Contexts" mas aria-label mantém a string completa. Hash routing seguindo gramática #<tab>[?key=val]. Auth obrigatória via Bearer token em header Authorization ou cookie — primeiro load via URL ?token=<value>. Hash #memories ainda ativa a tab Spec Context Projects (back-compat).
  3. Spec Context Projects: card por Spec Context Project ativo (state: ativo); o is_primary=True ganha border-left accent + bg tintado + badge "primary" e aparece em first-position no grid auto-fill. Cada card linka architecture.html, tech-stack.html, product/index.html daquele contexto. Memory view permanece two-route split: /memory-view/<slug>/<file> (wrapper com back-bar + iframe) → /memory/<slug>/<file> (verbatim Path.read_bytes()). Byte-identity preservada por construção (SPEC-DOC-008).
  4. Agents: agents.js (IIFE module) faz fetch('/api/agents?active_window_days=N') lazy on tab activation (default N=30, range 1–365). Card grid (repeat(auto-fill, minmax(360px, 1fr))) com header (status badge + nome + descrição + tier sub-label "T1 Orchestrator" / "T2 Curator" / "T3 Leaf"), 3-stat row mostrando telemetria real (sessions / total_cost_usd / last_activity_at — sourced do agent-monitoring reader Claude que extrai agent_name de tool_use.input.subagent_type em invocações Task tool de subagents despachados; rows com session_count = 0 ainda renderizam "Never" / "—" / "0"), skills chips, e expand chevron. Multi-open accordion: vários cards podem ficar expandidos simultaneamente. Expansão revela skills detalhadas + cost-by-context bars + system prompt fetched lazily via GET /api/agents/<id>/prompt (JSON wrapping o markdown). Enter key também expande. Source canônica: MarkdownAgentStore lê os 16 arquivos em .dadaia/agentic/agents/<name>.md e a aba renderiza exatamente 16 cards — telemetria de nomes desconhecidos é silenciosamente descartada. Visual identity por tier: cada card carrega data-tier="${agent.tier}" derivado do tier: frontmatter (T1=2 orchestrators, T2=1 curator, T3=13 leaf specialists); CSS aplica border 2px default (var(--color-border-card, #dddddd)) + 4px left accent em token tier-specific. Tokens: --color-tier-1 / --color-tier-2 / --color-tier-3 definidos para cada uma das 3 paletas (Mint / Sage / Warm) = 9 hex values total, todos WCAG 2.2 AA contra o card background. Missing tier: no markdown → default 3 + stderr warning; invalid → MissingTierError hard fail.
  5. Workflows: workflows.js (IIFE module) faz fetch('/api/workflows') lazy. Card grid (repeat(auto-fill, minmax(280px, 1fr))) com header (nome canônico — "tdd-cycle", "cross-cutting-feature", etc., não nomes de skill), description, agent chips, e stats footer (N stages · N gates · N parallel groups). Clicar em "View DAG" navega para #workflows?detail=<name>, dispara GET /api/workflows/<name> e renderiza detail view com DAG SVG server-rendered via longest-path layout (sem Mermaid, sem JS de layout). Loading skeleton enquanto a request está em voo. SVG tem role="img" + <title> + per-node aria-label. "Back to Workflows" restaura o grid e limpa o hash. 12 workflow cards (1 por arquivo em .dadaia/agentic/workflows/).
  6. Sessions: sessions.js (IIFE module) faz fetch('/api/sessions?runtime=' + Runtime.get() + '&limit=…') lazy on tab activation. Tabela ordenável (não cards — dado é comparison-oriented e numeric) com colunas Session / Project / Model / AI Turns / Context / Cost / Last activity / Status, sortável client-side por qualquer coluna; row click abre drawer populated por GET /api/sessions/<runtime>/<session_id> com timeline references. Cada row tem status dot (active verde / idle amarelo / ended cinza) e tooltip da coluna Session expõe o ai_title (operator-generated text complementar ao session_id[:8] slug). Coluna Context renderiza context_size_tokens = input_tokens + cache_creation_input_tokens + cache_read_input_tokens da última assistant event (working set real que o modelo recebeu, não o naked input_tokens enganoso pós-cache-warm). Coluna AI Turns renderiza message_count = COUNT(events) (events table só armazena assistant turns; honest naming evita user-message confusion). Auto-refresh loop de 10s pausado quando document.hidden === true (zero telemetry hits e zero battery drain quando tab está em background). Badge "Last updated" tick a ≤11s. Quando Runtime.get() === "codex", sessions.js renderiza banner top-of-table "Cost not tracked for Codex" e coluna Cost vira — em toda row (Codex adapter seta cumulative_cost_usd = None, cost_known = false). Toggle para Claude → banner some, Cost cells re-populam.
  7. Servers: panel.js faz fetch('/api/servers') a cada 5s e swap do <tbody> agrupado. Best-effort project.lower() == repo_slug.lower() contra contextos ativos; unmatched cai em grupo "Outros". TTL formatado client-side como duração relativa. Sub-seção "Unregistered listeners" (role="region") lista listeners descobertos via dadaia server scan; cada linha com lan_exposed: true recebe badge amarelo (bind 0.0.0.0). Payload de /api/servers não contém mais o campo dead unregistered.
  8. Theme switcher: botão visível no topbar abre dropdown com 3 opções (Mint / Sage / Warm). Selecionar uma seta data-theme="<name>" no root, atualiza tokens visíveis em tempo real, e persiste em localStorage["dadaia-panel-theme"]. Próximo reload aplica via pre-paint script. Escape fecha o dropdown e devolve foco ao trigger. Warm tem focus-visible com double outline para passar WCAG; axe-core PASS nas três paletas em Agents e Workflows.
  9. Runtime switcher: control adjacente ao theme switcher no topbar (Claude / Codex toggle, accessible labelling, color-coded via --color-runtime-claude warm gold / --color-runtime-codex sage green / --color-runtime-active resolvido por [data-runtime="…"] selectors — 9 hex tokens total = 3 cores × 3 paletas Mint/Sage/Warm, todos WCAG 2.2 AA contra topbar background). window.Runtime expõe get() -> "claude"|"codex" (default "claude") e set(value) que escreve em localStorage["dadaia-panel-runtime"] e emite dadaia:runtime-change CustomEvent + seta document.documentElement.dataset.runtime. agents.js, workflows.js e sessions.js subscrevem o event; on change: drop cache + refetch com ?runtime= appended à URL. Backend (render_api_agents_canonical, render_api_workflows_list, render_api_sessions, render_api_session_detail) lê runtime = qs.get("runtime", "claude") e filtra por provider column. NFR5 backward-compat: quando ?runtime= é omitido, default é claude — scripts antigos que chamam /api/agents ou /api/workflows sem o param recebem byte-identical o mesmo shape que recebiam antes (codificado em test_api_agents.py parity assertion).
  10. Shutdown: Ctrl+C envia SIGINT; signal handler spawn daemon thread que chama server.shutdown(), processo exita 0 e libera a porta em ≤2s.

Trigger típico

O operador quer visão de controle do workspace: trocar de tema, conferir quais agentes estão ativos e seu custo cumulativo, inspecionar a DAG de um workflow antes de despachar, abrir a memory HTML de um Spec Context Project sem sair da janela, e ver se algum dev server está LAN-exposed. Critério mecânico: se precisa de uma janela única para enxergar e operar o workspace, ele roda dadaia panel. Para CI, headless e automação, a CLI direta continua a interface canônica.

Diferencial

Sem este panel, o workspace é invisível ao operador casual: precisa-se ler markdown para descobrir agentes e workflows, abrir editores para conferir memory HTML, rodar dadaia server list para ver portas. A dashboard legacy (dadaia server dashboard) cobria só portas — single-purpose, footgun de bind 0.0.0.0, sem identidade visual. O panel pós-R3 unifica em quatro abas, com três decisões load-bearing: (1) sources canônicas — agentes vêm de .dadaia/agentic/agents/*.md, workflows de .dadaia/agentic/workflows/*.md, telemetria é overlay; o cardinal é fixo (10 agents / 12 workflows) e nomes desconhecidos somem; (2) DAG server-side em SVG via longest-path layout — zero Mermaid no browser, zero JS de layout, SVG cacheado por mtime, accessibility built-in; (3) 3 paletas axe-clean com tokens CSS extensíveis ([data-theme="X"]) — adicionar uma 4ª palette é uma PR trivial, sem reabrir release. A two-route split de memory permanece (/memory/ verbatim + /memory-view/ wrapper) como defesa estrutural de SPEC-DOC-008. Stdlib-only mantém custo de manutenção trivial e zero novas dependências.

Estado runtime tocado

  • Read: .dadaia/states/server_registry.json (registry de dev servers), .dadaia/states/spec_contexts.json (contextos ativos), .dadaia/agentic/agents/<name>.md (10 arquivos canônicos), .dadaia/agentic/workflows/<name>.md (12 arquivos canônicos), repos/<slug>/specs/memory/<path> (memory HTML + assets), telemetria local stdlib via agent-monitoring — todos via Path.read_bytes() sem mutação.
  • Write: nenhum — o panel é read-only. Não toca specs/memory/* (preserva atomicidade), não escreve em server_registry.json, não se registra a si mesmo no registry.
  • HTTP routes: GET /, GET /api/servers (sem o campo dead unregistered), GET /api/contexts, GET /api/agents?active_window_days=N&runtime=claude|codex (canonical overlay + sub-objeto telemetry, default 30, range 1–365; ?runtime= default claude per NFR5), GET /api/agents/<id>/prompt (JSON wrapping markdown; regex ^[A-Za-z0-9_-]+$ + Path.resolve().is_relative_to(base) defence-in-depth; 400 invalid, 404 unknown), GET /api/workflows?runtime=claude|codex (LIST lean — summaries, sem stages, sem diagram_svg; ?runtime= default claude), GET /api/workflows/<name> (DETAIL — stages[] + diagram_svg; mesma defesa), GET /api/sessions?runtime=claude|codex[&project=<slug>][&limit=<n>] (lista de SessionRow com campos session_id / runtime / project / cwd / model / started_at / last_activity_at / message_count / context_size_tokens / cumulative_cost_usd / cost_known / status / agent_name / ai_title), GET /api/sessions/<runtime>/<session_id> (detail), GET /memory/<slug>/<path>, GET /memory-view/<slug>/<file>, GET /static/<name> (Content-Type table travada em SPEC §6); unknown → 404 minimal.
  • Asset modules: features/panel/views/assets/css/ e features/panel/views/assets/js/ são módulos Python com string constants que features/panel/views/static.py serve via /static/<name> com Content-Type por extensão (.css → text/css; charset=utf-8, .js → application/javascript; charset=utf-8, .svg → image/svg+xml, etc.). Sem filesystem read no request path — não há traversal possible.
  • Auth + headers: Bearer token via secrets.token_urlsafe(32) em ~/.dadaia/state/panel.token (chmod 600); validação constant-time; 401 sem header válido para todos os endpoints /api/*. CSP default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' em HTML; X-Content-Type-Options: nosniff em JSON. Drop de 'unsafe-inline' do script-src é candidato nomeado para o primeiro hotfix post-R3.
  • Bind: 127.0.0.1 hard-coded; --bind aceita apenas "127.0.0.1".
  • Theme persistence: localStorage["dadaia-panel-theme"] recebe "mint" | "sage" | "warm"; root element ganha data-theme attribute pre-paint via inline script no <head>.
  • Runtime persistence: localStorage["dadaia-panel-runtime"] recebe "claude" | "codex" (default "claude"); root element ganha data-runtime attribute via window.Runtime.set(); mudança emite dadaia:runtime-change CustomEvent consumido por agents.js, workflows.js e sessions.js para refetch com ?runtime= appended.

Dependências

  • Roda sobre server-registry (consome .dadaia/states/server_registry.json), context-management (consome .dadaia/states/spec_contexts.json), agent-monitoring (consome TelemetryService via DI para as abas Agents, Workflows e Sessions — telemetria como overlay sobre a source canônica; Sessions consome TelemetryAggregator.list_sessions / get_session com RuntimeAdapter registry resolvendo Claude vs Codex enrichment per row) e public-asset-distribution (consome .dadaia/agentic/agents/ e .dadaia/agentic/workflows/ como sources canônicas dos cards).
  • specs-doctor protege a invariante SPEC-DOC-008 (byte-identity do memory HTML servido). Canary unit test em tests/unit/features/panel/test_views_memory.py falha fast se alguém introduzir mutação em views/memory.py.
  • sdd-gate-v3 não é tocado — panel é read-only e nunca escreve em specs/memory/*.
  • Tokens visuais: as três paletas (Mint / Sage / Warm) consomem tokens base de brand-identity e estendem via [data-theme="<name>"] selectors. Warm carrega regra focus-visible dedicada (double outline) para passar WCAG AA contrast.
  • Sem novas runtime deps: http.server.ThreadingHTTPServer, pathlib, json, webbrowser, signal, threading, secrets, e pyyaml (já declarado em tech-stack para parsing de frontmatter dos agentes/workflows). Renderização do DAG é Python puro (longest-path layout em string-templated SVG); Mermaid permanece carregado apenas dentro dos iframes de memory view (mesmo origin).
