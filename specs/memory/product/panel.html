Propósito

O Dadaia Workspace Panel é a UI local single-page servida em http://127.0.0.1:4999/ que dá identidade visível ao workspace. Substitui o utilitário isolado dadaia server dashboard por uma superfície unificada com três áreas de navegação: Servers (registry de dev servers entre projetos, evoluindo a dashboard legacy), Memories (memory HTML de cada Spec Context Project ativo servido verbatim via reverse proxy com back-bar CSS), e Agents & Workflows (placeholder card reservando espaço para o catálogo Release-2 de agentes e workflows multi-agente).

Resolve um gap de identidade: dadaia hoje é uma CLI Python + um sistema de assets agentic — invisível sem ler markdown ou rodar comandos. O panel torna o produto navegável: o operador clica de uma tab para outra, vê o estado dos contextos ativos, segue links para memory HTML preservando a atomicidade SPEC-DOC-008, e tem o contexto consolidado em uma janela. Boot via dadaia panel, bloqueia o terminal, bind loopback-only, zero deps em runtime — http.server da stdlib é o web tier inteiro.

Fluxo de uso

  1. Boot: operador roda dadaia panel a partir da raiz do workspace. Comando bind 127.0.0.1:4999 via ThreadingHTTPServer (stdlib), imprime Panel running at http://127.0.0.1:4999/, chama webbrowser.open() a menos que --no-open, e bloqueia até SIGINT.
  2. Index: GET / renderiza HTML com 3 sections + abas. Servers é a tab default. Tab switching client-side via panel.js (toggle aria-selected + hidden) — sem router server-side.
  3. Servers: panel.js faz fetch('/api/servers') a cada 5s e swap do <tbody> agrupado. Best-effort project.lower() == repo_slug.lower() contra contextos ativos; unmatched cai em grupo "Outros". TTL formatado client-side como duração relativa ("6h 42m").
  4. Memories: card por Spec Context Project ativo (state: ativo); o is_primary=True ganha border-left accent #7ec8e3 + bg tintado #f0faff + badge "primary" e aparece em first-position no grid auto-fill. Cada card linka architecture.html, tech-stack.html, product/index.html daquele contexto.
  5. Memory view (two-route split): clique no link navega para /memory-view/<slug>/<file> que retorna um wrapper de 40px com back-bar "← Voltar ao Painel" + <iframe src="/memory/<slug>/<file>">. A rota /memory/<slug>/<file> retorna Path.read_bytes() verbatim — byte-identity preservada por construção (sem template, sem injeção de head, sem mutação de body). Mermaid CDN funciona dentro do iframe (mesmo origin).
  6. Shutdown: Ctrl+C envia SIGINT; signal handler spawn daemon thread que chama server.shutdown() (idiom stdlib para evitar deadlock contra o serving loop), processo exita 0 e libera a porta em ≤2s.

Trigger típico

Sessão de operador que precisa de visão consolidada do workspace: portas em uso por dev servers de agentes em paralelo (server-registry), estado das memory HTML de cada Spec Context Project, navegação rápida entre arquitetura/tech-stack/catálogo de produto sem abrir múltiplos editores. Critério mecânico: se o operador quer ver o workspace, ele roda dadaia panel. Para qualquer outro caso de uso (CI, headless, automação), a CLI direta continua a interface canônica.

Diferencial

Sem este panel, o workspace é invisível: precisa-se ler markdown para descobrir o catálogo de produto, abrir editores para conferir memory HTML, rodar dadaia server list para ver portas. A dashboard legacy (dadaia server dashboard) cobria só portas — single-purpose, footgun de bind padrão 0.0.0.0, sem identidade visual. O panel unifica as três superfícies em uma navegação única, herda tokens visuais verbatim de specs/memory/architecture.html para coerência visual, e usa two-route split (/memory/ verbatim + /memory-view/ wrapper com iframe) como defesa estrutural da atomicidade SPEC-DOC-008: por construção é impossível alguém injetar conteúdo no body da memory HTML servida — o wrapper vive em uma URL separada. Stdlib-only mantém custo de manutenção trivial e zero novas dependências (NFR-1).

Estado runtime tocado

  • Read: .dadaia/states/server_registry.json (registry de dev servers), .dadaia/states/spec_contexts.json (contextos ativos), repos/<slug>/specs/memory/<path> (memory HTML + assets) — todos via Path.read_bytes() sem mutação.
  • Write: nenhum — o panel é read-only. Não toca specs/memory/* (preserva atomicidade), não escreve em server_registry.json, não se registra a si mesmo no registry.
  • HTTP routes: GET /, GET /api/servers, GET /api/contexts, GET /memory/<slug>/<path>, GET /memory-view/<slug>/<file>, GET /static/<name>; unknown → 404 com mensagem constitution-compliant.
  • Bind: 127.0.0.1 hard-coded em Release-1; --bind aceita apenas "127.0.0.1". Mesmo fix aplicado à legacy dadaia server dashboard (FR-7 — substituição de "localhost" por "127.0.0.1" explícito em cli/commands/server.py).
  • Path traversal guard: views/memory.py rejeita paths normalizados que escapem repos/<slug>/specs/. Assets estáticos (panel.css, panel.js) são Python string constants em views/_assets.py — não há filesystem read, não há traversal possible (R1 packaging-friendly).
  • Deprecation: dadaia server dashboard emite warnings.warn(..., DeprecationWarning, stacklevel=2) + linha em stderr [deprecation] 'dadaia server dashboard' will be removed in a future release. Use 'dadaia panel' instead. Behavior preserved por uma release.

Dependências

  • Roda sobre server-registry (consome .dadaia/states/server_registry.json) e context-management (consome .dadaia/states/spec_contexts.json).
  • specs-doctor protege a invariante NFR-2 / SPEC-DOC-008 (byte-identity do memory HTML servido). Canary unit test em tests/unit/features/panel/test_views_memory.py falha fast se alguém introduzir mutação em views/memory.py.
  • sdd-gate-v3 não é tocado — panel é read-only e nunca escreve em specs/memory/*.
  • Sem novas runtime deps: http.server.ThreadingHTTPServer, pathlib, json, webbrowser, signal, threading — tudo stdlib.
  • Tokens visuais: panel.css reproduz verbatim a paleta de specs/memory/architecture.html (#fafafa bg, #222 texto, #2d7d9a links de body-text WCAG AA, #7ec8e3 apenas como accent decorativo).
