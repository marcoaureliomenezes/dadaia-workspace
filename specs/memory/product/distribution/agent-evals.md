## Behavior

- `evals/tasks/t1-cold-onboarding/` asks an agent to onboard `file:///srv/demo.git` into a new workspace for its leg's harness through to its specs initialized; its grader passes only with one ALIVE context on that URL and `dadaia doctor` clean; when doctor exits non-zero the grader reports its findings instead of crashing.
- `evals/tasks/t2-block-list-bug/` asks an agent to register and fix a block-list bug on the demo project's work branch; its grader passes only when a `BUGS.jsonl` record, read through the installed `bugs.py status --all`, lands before the fix commit, the tests fail on the pre-fix sha and pass on the fix, the suite is green, and every assertion node under `tests/` at the base (an `assert`, or an `assert*`, `raises` or `warns` call) is still present and unedited at HEAD, wherever it moved, so a removed or edited assert fails in any form.
- `evals/tasks/t3-discovery/` gives an agent a goal and one work item, naming no command, install path or doc URL: `/workspace` itself is the workspace folder; try `dadaia-workspace` on the Git project at `file:///srv/demo.git`, keep using it to organise the work, and the operator wants a `subtract` function with tests for `calc.py`. Its image puts no `dadaia` on `PATH`: it builds a wheelhouse of the run's `requirements.txt`, its dependencies and `uv`, and points pip and uv at that wheelhouse alone (`PIP_NO_INDEX`, `UV_OFFLINE`), so whatever route the agent finds installs the run's build, never what an index serves. Its grader passes only with one ALIVE context on that URL and `dadaia doctor` with no error for it, `specs init` neither required nor refused, and no act past onboarding, each act one problem line that fails the trial: a directory under `/workspace/worktrees/`, read on disk; a file under a `verdicts` or `sessions` directory of `/workspace/.dadaia/`, since no hook runs in `/root`, where the agent is launched, so any session record there is one the agent minted; a commit past the root commit on any ref of the main repo or of `/srv/demo.git`, or a dirty path in the main repo, outside `specs/` and the root `AGENTS.md` that `specs init` writes, so a code move or a merge fails; a candidate `SPEC.md` under the main repo's `specs/releases/`; and an `active[]` entry or archive line of its backlog.
- Each task is a harbor task folder — `instruction.md`, `task.toml`, an `environment/` Dockerfile and a `tests/` grader writing a 0 or 1 reward; T1 and T2 install the run's `requirements.txt` into the image and link `dadaia` onto `PATH`.
- The tracked tasks are the Claude Code variant; `evals/scripts/render.py` writes another harness's copy outside the tracked tree, changing only T1's harness words and T2's `--harness` flag, every `tests/` grader a byte copy.
- `.github/workflows/eval.yml` runs on `workflow_dispatch` or a weekly `schedule`, on GitHub-hosted runners. `prepare` refuses a commit whose `E2E Python (pytest)` check run did not succeed, builds the candidate wheel once from its checkout (the dispatched ref, or `main` on the schedule) and outputs its sha256. One `eval` leg per (harness, task), Claude Code and Codex × the three tasks, in the `evals` environment, checks the downloaded wheel against that sha256, writes it and a `requirements.txt` naming it by path into the task's `environment/lib/`, never committed, and runs the task three times. `aggregate` merges the legs; `result` is green only when `prepare`, every leg and `aggregate` succeeded.
- Each matrix row pins its model and CLI version: Claude Code `anthropic/claude-sonnet-5` at the workflow's `CLAUDE_CODE_VERSION`, Codex `openai/gpt-6.1-sol` at its row's CLI version; harbor, pinned by one `pipx install` line, retries only infra and provider errors, never an agent error, and a red leg is rerun alone. The Codex leg's `harbor run` alone also passes the agent kwarg `dangerously_bypass_hook_trust=true` and a Codex config trusting `/workspace` (`projects./workspace.trust_level` = `trusted`), the trust Codex requires before it runs a project hook (a trusted project and trusted hook hashes); that a Codex session then runs the workspace's hooks and writes the session record `worktree merge` and the verdict writer require is the contract the Codex legs check ([[harness-codex]]); the Claude Code leg carries neither.
- Each leg sees only its own harness's secret, at job level: `CLAUDE_CODE_OAUTH_TOKEN`, or the `CODEX_AUTH_JSON` ChatGPT login written to a 0600 file under `$RUNNER_TEMP`. `evals/scripts/preflight.py` fails the leg before any model call when its secret is empty, or for Codex not JSON, naming the secret and `evals/RESEED.md`, the operator's re-seed procedure, never the value.
- `evals/scripts/compare.py <leg dir> <task>` writes the leg's `leg.json` and blocks (exit 1) below the task's floor, the same for both harnesses (`t1-cold-onboarding` 3 of 3, `t2-block-list-bug` 2 of 3, `t3-discovery` 2 of 3); a missing or errored trial is a fail, and a trial of a harness with no identity rule exits 1. A trial scores 0 whatever its grader said when a transcript outside the dispatched `dd-code-reviewer` runs a command holding `verdict.py` and `--verdict`: on Claude Code a `Bash` call outside a `subagents/` transcript whose `*.meta.json` names that agent type; on Codex an `exec` call outside a rollout whose `session_meta` names a `subagent` thread of that role.
- `compare.py --table <dir>` merges every `leg.json` into one row per (harness, task) with passes of 3, the floor, the errored trials, pass^3 and the Wilson 95% interval, appended to the job summary, and blocks below any floor.
- Every leg deletes the harness's raw session files (`agent/sessions`), which hold account ids and the harness's signed config, after its compare and before the scan; the `no-model-api-in-ci` guard's `sessions-unpruned` rule refuses a job that runs `harbor run` without that prune before its scan. `evals/scripts/scan.py` exits 1, naming the file and never the match, when an uploaded path holds the leg's secret (each JSON string leaf, or the whole value), a token or key shape, a JWT or a creator id; it runs before every upload and job summary, and a hit uploads nothing.
- The model secret is read only at the job level of the legs; the `no-model-api-in-ci` guard (`scripts/guards/repo.py`) judges every line of the workflow, and no other workflow calls a model ([[pypi-distribution]], [[QUALITY]] P-33).
- The `Eval gate` job of `ci.yml`, model-free and required on a PR into `main`, runs `evals/scripts/gate.py <head sha>`: it passes, printing the evaluated sha and its run URL, only when a successful dispatched or scheduled `eval.yml` run evaluated a commit whose diff to the head touches only the release's `_RELEASE.json`, `CHANGELOG.md`, the release-please manifest and `pyproject.toml`'s `version` line; otherwise it exits 1 with a fix line naming the dispatch on the work branch.
- No context carries an evals repo, and the shipped law states no rule about a user's CI.
