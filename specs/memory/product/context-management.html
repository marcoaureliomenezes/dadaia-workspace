context-management

CLI surface: dadaia context {create|list|show|activate|deactivate|promote|delete|use} · dadaia {release|backlog|bug} new · dadaia memory product add · dadaia migrate tree-v2 · Closure: spec-context-tree-v2

Propósito

Gerencia múltiplos Spec Context Projects — cada um mapeia nome → repo_slug → repo_url e tem state machine (inativo ↔ ativo). Um context ativo é clonado em repos/<repo_slug>/ e suporta promoção a primary (o context default usado por agentes e gates).

Permite ao operador trocar entre projetos/branches em paralelo sem criar múltiplos workspaces, e mantém um único primary explícito em .dadaia/states/primary_context.json que outras features (gate, orchestration, public install) leem para resolver caminhos.

Canonical specs/ tree v2 (scaffold baseline pós spec-context-tree-v2)

O scaffold de novo consumer repo (dadaia init + dadaia context create) entrega a árvore v2:

  • specs/constitution.md — leis absolutas do produto.
  • specs/memory/architecture.html e specs/memory/tech-stack.html — memory HTML atômica (Markdown depreciado).
  • specs/memory/product/index.html — entry point do catalog; dadaia memory product add <slug> cria feature HTML e regenera o index.
  • specs/backlog/, specs/bugs/, specs/releases/ — diretórios de lifecycle com README.md e .gitkeep.
  • specs/AGENTS.md — contrato SDD do spec tree para o operador do consumer repo.
  • Removidos do scaffold: specs/foundation/ (depreciado) e specs/SPEC.md na raiz (pre-release-model).

Doctor TREE-1..7 enforça e repara esta árvore: dadaia specs doctor em workspace recém-scaffoldado deve sair com 0 violations.

CLIs de criação de artefatos SDD (evitam frontmatter manual):

  • dadaia release new <id> — cria specs/releases/<id>/SPEC.md stub com frontmatter canônico (slug validado; não-destrutivo se já existe).
  • dadaia backlog new <slug> — cria specs/backlog/<slug>.md stub.
  • dadaia bug new <slug> — cria specs/bugs/<slug>.md com session_id: null.
  • dadaia memory product add <slug> — cria feature HTML em specs/memory/product/<slug>.html e regenera index.html de forma idempotente.

Migration path para consumer repos existentes: dadaia migrate tree-v2 move specs/foundation/ → specs/releases/legacy/foundation/ e specs/SPEC.md → specs/releases/legacy/SPEC.md de forma atômica e idempotente.

Fluxo de uso

  1. dadaia context create my-feature --repo dadaia-workspace — registra o context (inativo, sem clone).
  2. dadaia context activate my-feature — clona o repo em repos/dadaia-workspace/, faz checkout da branch, marca ativo e promove a primary se for o único ativo.
  3. dadaia context list — mostra todos com state, primary marker, repo slug.
  4. dadaia context promote other-ctx — move o primary status; dispara reinstall de public assets para alinhar projeções com o novo primary.
  5. dadaia context deactivate — git sync, remove o repo do disco, volta a inativo.
  6. eval "$(dadaia context use my-feature)" — seta apenas DADAIA_CONTEXT na shell corrente, sem mutar o estado global. Útil para sessões one-off.

O hook .dadaia/scripts/ctx-inject.sh (instalado por workspace-init) executa em cada UserPromptSubmit e injeta DADAIA_CONTEXT a partir de primary_context.json — assim agentes auto-descobrem o context sem flags explícitas.

Trigger típico

Quando o operador vai começar a trabalhar em um repositório novo, ou alternar entre projetos paralelos sem fechar o workspace.

Diferencial

Sem context management, agentes precisariam de paths absolutos hardcoded ou flags em cada comando. A state machine inativo/ativo + primary garante que o gate, orchestration e public install sempre conhecem inequivocamente onde está o "projeto atual". Promote dispara reinstall de assets, garantindo que .claude/ reflete o context certo.

Estado runtime tocado

  • .dadaia/states/spec_contexts.json — registro de todos os contexts (state, primary flag, repo metadata)
  • .dadaia/states/primary_context.json — qual é o primary corrente (repo_slug + specs_dir)
  • repos/<repo_slug>/ — repo clonado durante activate, removido em deactivate
  • .claude/ e outras projeções — reinstaladas em promote
  • DADAIA_CONTEXT env var — exportada por use ou pelo hook

Dependências

  • Depende de workspace-init (cria spec_contexts.json e o hook ctx-inject).
  • Activate/promote dispara public-asset-distribution internamente.
  • agent-orchestration e sdd-gate-v3 consomem o primary context para resolver paths.
