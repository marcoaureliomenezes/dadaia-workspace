# specs/memory/AGENTS.md — Memory Directory Contract

> **Scope:** This file governs the `specs/memory/` directory. It is the first file an
> agent should read when entering this directory. It answers "what can I do here and how?"

---

## 1. Read contract (all agents)

A lean memory bootstrap (tech-stack + feature catalog) is **injected at session start**
via `ctx-inject.sh` (Claude Code / OpenCode) or the `memory-ctx` Codex adapter — if
present, it is already in your context. If not (standalone session), read them yourself.

In ALL cases, before starting work:

1. Read `product/catalog.json` (or `product/index.html` if catalog absent) and identify
   the 1-3 features most relevant to your task.
2. Self-pull `architecture.html` — layer rules, dependency contracts, agent topology.
   Architecture is **NOT injected** (it is large); ALWAYS pull it before any architectural,
   cross-layer, or design decision.
3. Self-pull `product/<slug>.html` for each relevant feature (1-3 files).

This mirrors the `dadaia-workspace-spec-navigator` skill and the Step 0 block in every
agent persona. Do NOT skip steps 1-3 before implementation, review, or analysis.

---

## 2. Write contract (product-engineer only, CLOSURE phase)

All `*.html` and `product/*.html` files in this directory are **write-locked**.

- Gate enforcement: **RULE A** in `sdd-spec-gate.sh` blocks every write to
  `specs/memory/**` for any agent other than `product-engineer` during the CLOSURE phase.
- The lock is hard — not a warning. An agent that attempts to write a memory file during
  IMPLEMENTATION will be blocked by the gate.
- If memory is discovered to be stale during IMPLEMENTATION, file a bug report via
  `dadaia bug new <slug>` and continue working. Memory updates happen at the next CLOSURE.

---

## 3. Atomicity contract

Memory describes the product **as it is now**. No Changelog. No History section.
The delta between the previous state and the current state lives in `git log`. Memory
atoms are always a point-in-time snapshot — they must be read as truth, not as a diff.

---

## 4. File manifest

| File | Role | Content type |
|------|------|--------------|
| `architecture.html` | Layer rules, ADRs, agent topology | HTML (write-locked) |
| `tech-stack.html` | Approved toolchain and constraints | HTML (write-locked; **injected** at session start) |
| `product/index.html` | Human-browsable feature catalog | HTML (write-locked) |
| `product/catalog.json` | Machine-readable feature index | JSON (generated; **injected** at session start) |
| `product/<feature>.html` | Per-feature detail atom | HTML (write-locked; self-pull on demand) |

`architecture.html` is self-pull only (not injected). Check whether `product/catalog.json`
exists before reading: if present, prefer it over `product/index.html` for feature navigation.

---

## 5. Generation note for `catalog.json`

`catalog.json` is **generated, not hand-edited**. It is regenerated by:

- `dadaia memory catalog generate` CLI command (or equivalent `dadaia memory product add`
  plumbing) when a new feature HTML is added.
- `product-engineer` during the CLOSURE phase of any release that adds, removes, or
  reorders features in the catalog.

If the file is absent or stale, run `dadaia memory catalog generate --specs-dir <path>`.
Never edit `catalog.json` by hand — the next generation run will overwrite your changes.
