Security Threat Model — Agent Monitoring via dadaia-workspace Panel

Operator lema: "Users will use the dadaia-workspace in its own environment. The dadaia-workspace panel must be secure. And the workspace resilient."

Supply-chain principle: "If we can get all we need from the providers, it is the better and safest solution." Every proposed new dependency is evaluated against this bar.

1. Threat Matrix

MEDIUM Network filesystem truncation; Claude Code bug writing partial JSON; an agent writing to the file maliciously (see T7). Each line must be parsed inside a try/except block; parse failures skip the line and advance the checkpoint. Checkpoint must be byte-offset based, not line-number based, to survive truncation. Log the failure (without echoing the line content, which may contain secrets) with the file path and byte offset only. software-engineer

MEDIUM Operator inadvertently runs sudo dadaia panel start; cron job runs as root. Reader must assert os.getuid() != 0 at startup and refuse to proceed if running as root. MEDIUM A rogue agent (running as the same uid as the operator) with write access to ~/.claude/projects/ appends crafted JSONL lines with inflated token counts. Full cryptographic signing of each jsonl line is not feasible (Claude Code is a provider black box — we do not control what it writes). Practical mitigations: (a) reader validates that usage.* fields are non-negative integers within plausible bounds (e.g., max 2,000,000 tokens per event — above this, mark event as suspect and log without accumulating); (b) UI surfaces a "data integrity warning" banner if any session contains a suspect event; (c) reader records the file modification time and inode at checkpoint creation — if the file is modified backwards (truncation followed by appending), flag the session. These are detective controls, not preventive. The threat model must document that an agent running as the operator uid is a trusted principal for purposes of file integrity. software-engineer (validation bounds) + product-engineer (UI warning design)

While these IDs do not expose content, they are persistent identifiers that could enable session enumeration if a screenshot is shared. LOW Operator shares a screenshot of the panel in a public channel (Slack, GitHub issue, etc.). Display only the first 8 characters of the sessionId followed by an ellipsis in all list and card views (e.g., abc12345...). The full sessionId may be exposed in a detail view accessible only on explicit interaction. This is sufficient to prevent trivial enumeration while preserving debugging utility. frontend-engineer
T10 SQLite corruption leaves panel unbootable — if the SQLite file is corrupted (e.g., mid-write crash, disk full, filesystem error), the panel crashes on startup rather than degrading gracefully. Document the recovery path: delete or move the corrupt file and restart; the reader will re-ingest from jsonl. This ensures resilience per the operator lema. software-engineer
T11 Rate limiting absent on local HTTP API — no rate limiting on 127.0.0.1:4999 means a tight local loop can exhaust the ThreadingHTTPServer's thread pool (or Python's GIL scheduling), degrading the panel for all consumers. LOW A buggy script or browser tab polling /api/agents in a tight loop. At this stage, a simple in-process request counter per 10-second window with a 429 response if exceeded (e.g., 60 requests/10s per IP — but since the binding is 127.0.0.1, all clients are 127.0.0.1, so a global rate limiter on the handler class is sufficient) is adequate. T12 Log rotation / deletion of aggregated SQLite — secure deletion of the SQLite file via rm only removes the directory entry; on most Linux filesystems data blocks are not overwritten, leaving telemetry recoverable from disk. Document in the operator guide that shred -u ~/.dadaia/state/telemetry.sqlite (or wipe) should be used for secure deletion, not plain rm. For a local single-user developer tool, this is informational rather than a blocking requirement. The SQLite file contains aggregated metadata only (no raw prompts), so the risk is low by design. product-engineer (documentation)

3. Local Auth Recommendation

Open question #7 from Phase 1: "Whether the local panel adds an auth token now that cost telemetry is exposed, or keeps 127.0.0.1 unauthenticated."

Recommendation: YES — add a shared-secret Bearer token for this release.

Rationale: The scope of what the panel exposes is fundamentally changing. The existing panel serves only static server status and memory files — data that an attacker could also read from the filesystem. The new panel will expose: sessionIds, cumulative token costs per agent per day, model usage patterns, and cwd paths that reveal workspace structure. This is a qualitatively different data class. The threat (T3) is real: any process running as the operator's uid (or connecting to localhost) can poll these endpoints silently.

Proposed model — minimal local token:

  • On first panel start, generate a random 32-byte token using secrets.token_urlsafe(32).
  • Persist the token in ~/.dadaia/state/panel.token with chmod 600.
  • Panel reads this file on startup and validates every request for a matching Authorization: Bearer <token> header.
  • Requests without a valid token receive 401 Unauthorized with no body.
  • The browser opens the panel via dadaia panel open, which reads panel.token and appends it as a query parameter on the initial redirect (?token=...<redirect to session cookie>) or sets it in a session cookie on first load.
  • Alternatively, the simpler path: the panel UI is served only after the browser supplies the token as a query parameter on first load; the token is embedded in the URL printed by dadaia panel start (http://127.0.0.1:4999/?token=ABC...).

What this does NOT protect against:

  • A process running as the operator's uid that reads panel.token directly — but such a process already has full filesystem access to all telemetry sources, so the marginal risk is nil.
  • A keylogger that intercepts the browser URL — but this is out of scope for a local developer tool.

Implementation cost: approximately 20 lines in handler.py's do_GET method, plus a token-generation step in the service startup sequence. Zero new dependencies (secrets is stdlib). This is proportionate — not a bazooka.

If the operator overrides to "no auth": the fallback mitigation is session ID prefix truncation (T9) + documented risk acceptance. Document the override as an explicit operator decision in the spec approval gate.

4. Hardening Recommendations (Prioritized)

  1. [CRITICAL — T1] Schema allowlist at the reader/aggregator layer. Before any data is written to SQLite or returned by any HTTP handler, pass every parsed event through an explicit allowlist function that retains only the approved fields. Fail closed: if a field is not in the allowlist, drop it silently. This is the single most important hardening measure in this release. The allowlist function must have its own unit tests.
  2. [HIGH — T2] Enforce chmod 600 on SQLite and parent directory on creation. Use os.chmod(path, 0o600) immediately after open(path, "w") or after the first sqlite3.connect(path). Check that the parent directory is 0o700. Add an assertion in the test suite.
  3. [HIGH — T3] Add local Bearer token auth. See Section 3 above. Use secrets.token_urlsafe(32), persist to ~/.dadaia/state/panel.token with chmod 600, validate in do_GET before dispatch to any route.
  4. [HIGH — T4] Enforce reader budget limits. Max 4 MB per file per polling tick. Max 64 KB per JSONL line (skip + warn if exceeded). Checkpoint byte offsets in SQLite. Cap in-memory event buffer at 10,000 events per cycle. These values must be named constants, not magic numbers.
  5. [MEDIUM — T5] Fault-tolerant JSONL line parsing with per-line try/except. Checkpoint must be byte-offset based. Log parse failures as: WARN: skipped malformed line at <path>:offset=<N> — never log the line content.
  6. [MEDIUM — T6] Refuse to start if os.getuid() == 0. One-line guard in TelemetryService.__init__. Print a clear error and exit 1.
  7. [MEDIUM — T8] Add CSP and X-Content-Type-Options headers. In handler.py:_respond, add for HTML responses: Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'unsafe-inline'. For JSON responses: X-Content-Type-Options: nosniff. No new dependency; three additional send_header calls.
  8. [MEDIUM — T7] Validate token count bounds. Reject events where any token count is negative or exceeds 2,000,000. Mark such events as suspect=True in SQLite rather than discarding them (preserves auditability). Surface a UI warning banner if any suspect events exist in the current view.
  9. [LOW — T9] Truncate sessionIds in all list/card views. Display sessionId[:8] + "..." in list views. Full ID only in a detail/tooltip context on explicit user interaction.
  10. [LOW — T10] Boot in no-telemetry mode on SQLite corruption. Run PRAGMA integrity_check at startup. On failure: rename corrupt file, log error, return 503 from all telemetry endpoints with a human-readable message.
  11. [LOW — T12] Document secure deletion in operator guide. shred -u ~/.dadaia/state/telemetry.sqlite for secure wipe. Plain rm is not secure on ext4/HFS+. This is documentation, not code.

6. Resilience Checklist

Per the operator lema: "the workspace resilient." These items must be verified before closing the implementation spec.

  • Panel starts successfully even if ~/.claude/projects/ does not exist (warn, no crash).
  • Panel starts successfully even if ~/.codex/state_5.sqlite does not exist (warn, no crash).
  • Panel starts in no-telemetry mode if telemetry.sqlite is corrupt (see T10).
  • Reader resumes correctly after an abrupt kill (checkpoint byte offset persisted before crash).
  • Reader handles a jsonl file that is actively being written by Claude Code (open in append mode) — use read-only open, do not lock the file.
  • Reader handles a jsonl file that is replaced (rotated by Claude Code) — detect via inode change on next polling tick, reset checkpoint for that file.
  • SQLite can be reconstructed from scratch by re-running the reader against all existing jsonl files — idempotent ingestion required (event deduplication by sessionId + timestamp + type).
  • Backup of SQLite: document that sqlite3 ~/.dadaia/state/telemetry.sqlite .dump > backup.sql is the correct method. No automated backup required in v1; document the manual procedure.
  • Panel HTTP endpoints return 503 (not 500/crash) when the telemetry service is unavailable.
  • Disk-full condition during SQLite write: reader catches the exception, logs it, and retries on the next polling tick without crashing the panel.

7. Specific Notes on Existing Code

handler.py — current state

The current handler.py has two relevant security controls already in place:

  • Path traversal guard: present in views/memory.py (referenced in the plan). The new /api/agents and /api/sessions endpoints do not serve filesystem paths and therefore do not require a path traversal guard. However, if any new endpoint accepts a slug or path capture group used to read a file, the existing guard from memory.py must be reused.
  • html.escape: already used in memory views. Any new HTML template fragment that includes user-derived data (e.g., agent name, model name, cwd path) must use html.escape. The current JSON API endpoints return bytes from json.dumps — this is safe, as json.dumps handles escaping for JSON context. Do not render JSON data directly into HTML strings without escaping.

_NOT_FOUND_BODY

The 404 body currently lists all valid routes. When new endpoints are added (/api/agents, /api/sessions, /api/workflows), update this constant to include them. This is a documentation gap, not a security issue, but omitting it causes confusing 404 messages for developers.

Missing security headers in _respond

The _respond method currently sends only Content-Type and Content-Length. It must be extended (not replaced) with the security headers described in hardening item #7 above. The extension should be conditional on content type: CSP only for HTML, nosniff for JSON. Implement as a separate private method _security_headers(content_type) to keep _respond readable.

9. Decisions Required from Operator

  • Auth token (Section 3): adopt the Bearer token model, or explicitly decline and document risk acceptance. Silence is not acceptable here — this is a named security decision in the spec.
  • Retention policy for SQLite aggregates: the Phase 1 report proposes perpetual retention for aggregates (only raw events capped at 180d). Confirm or set a different cap. No cap = unbounded SQLite growth on long-running workspaces.
  • Suspect event behavior (T7): mark as suspect and show UI warning, or silently discard? The recommendation is to mark + warn, but this is a product decision.
