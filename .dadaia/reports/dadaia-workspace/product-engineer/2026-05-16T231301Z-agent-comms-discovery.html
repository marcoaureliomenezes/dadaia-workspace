Discovery — agent-comms-v1

Phase 1 do pipeline PE Discovery → architect impact → SE rec → PE Synthesis → SE impl (D4). Este report é o input que o software-architect consumirá em sua análise de impacto; o software-engineer o usará em conjunto com o report do arquiteto para emitir sua recomendação técnica antes da Synthesis em Phase 5.

1. Executive Summary

Hoje, 10 dos 10 agentes em dadaia_workspace/public/agents/*.md declaram em frontmatter schema_ref: handoff-schema-v1 para os artefatos que produzem (21 ocorrências no canonical + projeções totalizando 82 ocorrências em 42 arquivos de assets distribuídos). Apesar disso, nenhum arquivo de schema existe no workspace (find dadaia-workspace/ -name "*.schema.json" retorna vazio; find dadaia-workspace/ -name "handoff*" retorna vazio). O input_contract introduzido no fechamento de GAP-INPUT-001 (ver specs/z_bug_specs.md linhas 126–131) prometeu um contrato declarado e referência ao handoff-schema-v1 — mas a referência aponta para vácuo. Pior: a feature de orquestração multi-agente (auditoria 2026-05-15-orchestration-audit.md finding HIGH "must_include declarado mas não validado") já carrega um campo análogo (must_include) sem enforcement; agentes downstream consomem outputs upstream sem validação de contrato. agent-comms-v1 resolve a dor funcional de "handoff prometido mas não verificável": materializa o schema, entrega o validador CLI dadaia reports validate, instala a skill dadaia-handoff-emitter e migra 2–3 agentes pilotos para emitir um sidecar *.handoff.json ao lado do report HTML. Além disso, esta release encerra a dívida do z_bug_specs.md dual (duas localizações, ambas referenciadas por skill+command+template) migrando todo o conteúdo aberto para specs/backlog/candidates.md e o histórico para specs/_archive/legacy-bug-specs/, eliminando uma das duas fontes de verdade paralela do projeto.

2. Functional Requirements (FRs)

Lista atomicamente verificável dos requisitos funcionais que este release deve cumprir. Cada FR é declarado de modo que possa virar um critério de aceite no SPEC de Phase 5.

FR1 — Schema JSON canônico do handoff existe e é projetado

O que: criar arquivo dadaia_workspace/public/schemas/handoff-v1.schema.json — JSON Schema Draft 2020-12 — descrevendo a estrutura mínima do sidecar *.handoff.json. Conteúdo mínimo (a refinar em SPEC): campos schema_version, agent, context, release_id, produced_at (ISO 8601), artifact (objeto com type, path, content_hash), findings (array opcional com severity), decisions_required (array opcional), next_handoff (objeto opcional com target_agent, expected_output_path).

Projeção: o pacote já distribui assets via dadaia_workspace/public/ → staging → .dadaia/agentic/ → .claude/ + .codex/ + .opencode/ + .agents/ (ref: constitution.md L106–119). O schema precisa de um novo subdiretório public/schemas/ além dos 6 existentes (agents/, commands/, rules/, skills/, scripts/, workflows/, templates/). Decisão de projeção a confirmar com o arquiteto em Phase 2: staging-only? ou também projetar em .claude/schemas/?

Critério de aceite: jq '.["$schema"]' dadaia_workspace/public/schemas/handoff-v1.schema.json retorna URL válida do meta-schema; dadaia public stage propaga o arquivo para .dadaia/agentic/schemas/; doctor verde.

FR2 — CLI dadaia reports validate

O que: novo subcomando Typer dadaia reports validate [<path>|--all] [--strict] que recebe ou (a) caminho explícito de um *.handoff.json ou um diretório, ou (b) --all que itera .dadaia/reports/<context>/**/*.handoff.json. Valida cada arquivo contra public/schemas/handoff-v1.schema.json. Exit code 0 quando todos passam; exit code 2 quando algum falha em modo strict; exit code 0 com warnings em stderr quando --strict=false (NFR2). Output JSON via --json (alinha com padrão das demais CLIs do produto, ex. dadaia context show --json).

Arquitetura: seguindo a regra CLI → Features → Core ← Infrastructure (constitution L52–69), o comando vive em dadaia_workspace/cli/commands/reports.py, a feature em dadaia_workspace/features/reports_validation/service.py, com Protocol em core/protocols/handoff_validator.py e implementação em infrastructure/jsonschema_handoff_validator.py. Adapter usa jsonschema (já não está na lista da constitution L17–28; requer decisão no Phase 5 grill-me: usar stdlib-only com check manual ou adicionar jsonschema ao tech-stack).

Critério de aceite: CLI listada em dadaia --help; comando passa em uma fixture válida e falha (exit 2) em uma fixture inválida; cobertura ≥ 80% na camada feature (constitution L131).

FR3 — Skill dadaia-handoff-emitter

Skill projetada em .agents/skills/dadaia-handoff-emitter/ e via projeções runtime-specific (constitution L117).

Critério de aceite: arquivo materializado; dadaia public stage && dadaia public install --target all projeta para 4 runtimes; dadaia public doctor retorna [ok] em todas as projeções da skill.

FR4 — Pilot agents emitem handoff.json

O que: 2–3 agentes pilotos (proposta em §6) recebem instrução explícita no system prompt (markdown body) para invocar a skill dadaia-handoff-emitter ao final de cada produção. Não há mudança no bloco input_contract do frontmatter — o schema_ref: handoff-schema-v1 já está lá hoje e passa a ter referente real após FR1.

Critério de aceite: ao rodar um workflow real que dispatcha cada um dos pilotos, todos os reports do piloto vêm acompanhados de .handoff.json ao lado; dadaia reports validate --all passa em modo non-strict (NFR2) e reporta os reports legados (de agentes não-piloto) como "missing handoff" mas sem falhar.

3. Non-Functional Requirements (NFRs)

NFR1 — Backwards compatibility total com reports legados

Reports HTML existentes em .dadaia/reports/<context>/<agent>/*.html permanecem válidos. A introdução do sidecar .handoff.json é puramente aditiva: nenhum consumer atual de reports HTML quebra. Isso inclui o OrchestrationService (features/orchestration/service.py) que hoje passa output_path entre stages como string — continua funcionando.

NFR2 — Janela de transição: --strict=false default em v1

dadaia reports validate tem flag --strict com default false em v1. Reports sem sidecar emitem warning, não erro. Em v2 (release futuro, fora do escopo D1) o default passa a true e o CI gate bloqueia merges com sidecars inválidos. Isso evita big-bang: os 8 agentes não-piloto migram em releases subsequentes sem bloquear este.

NFR3 — Zero novas dependências de runtime obrigatórias

A validação pode usar jsonschema (PyPI, maduro) ou check manual em stdlib. Como jsonschema não está na tech-stack approved (constitution L17–28), a decisão é entre: (a) adicionar à constitution via update formal (requires explicit operator confirmation per L451 do product-engineer.md) ou (b) implementar check manual sobre stdlib json (custo: ~80 linhas, sem capacidade de meta-schema). Decidir em Phase 5 grill-me.

NFR4 — Sem hook em CI para o validate em v1

Esta release não adiciona um job em .github/workflows/ci.yml que rode dadaia reports validate --strict. O escopo D1 limita à entrega de schema + CLI + skill + pilotos. Adicionar gate em CI é v2 (depende de NFR2: precisamos primeiro garantir que todos os 10 agentes emitem handoff confiavelmente, senão CI vermelho permanente).

NFR5 — Token-overhead budget <3%

O sidecar .handoff.json deve ser tipicamente < 2 KB. Para um report HTML médio de 50–70 KB (ref: 2026-05-15-orchestration-audit.md tem 46675 bytes, 2026-05-16T214645Z-hotfix-track.md tem 41339 bytes), o overhead é ~3% no pior caso. Limite verificável no validate via warning quando stat -c%s <file>.handoff.json > 4096. Esse warning não falha o validate, apenas sinaliza inflation.

NFR6 — Migração de z_bug_specs.md não quebra refine-specs flow

A ordem é estrita (ver §4 deletion order): primeiro patchear os 3 consumers para apontar a candidates.md, validar com dadaia public install --target all && dadaia public doctor, só então git rm os dois .md. Em nenhum ponto intermediário o fluxo de refine-specs deve apontar para arquivo inexistente.

NFR7 — Idempotência da projeção de assets

Adicionar public/schemas/ e a skill dadaia-handoff-emitter exige que FileSystemPublicAssetManager reconheça o novo tipo schemas (caso atualmente trate apenas os 7 tipos enumerados acima). Verificável: rodar dadaia public install --target all --force duas vezes e confirmar diff zero.

6. Pilot agents proposal

A pergunta é: dos 10 agentes que declaram schema_ref: handoff-schema-v1 (ver inspeção L46 do software-architect.md, L43–59 do product-engineer.md, etc.), quais 2–3 emitem .handoff.json primeiro?

Critérios de seleção

  1. Volume de handoffs por release: agentes que produzem > 1 artefato por release dão mais signal por unidade de esforço.
  2. Posição no pipeline canônico: agentes que sentam em pontos de fan-in/fan-out (i.e., consumem inputs múltiplos e produzem para múltiplos consumers) maximizam a utilidade do contrato verificável.
  3. Cobertura de fluxos críticos: agentes que estão envolvidos no workflow spec-refinement (o seed workflow mais usado, ver memory/product/agent-orchestration.html L46) são pilotos naturais.
  4. Risco de regressão: agentes que escrevem muitos arquivos diferentes (ex: product-engineer escreve discovery + SPEC + PLAN + TASKS + CLOSURE) têm mais variabilidade de output — bom para validar robustez do schema.

Análise por agente candidato

software-architect 1 output (arch_report) Pivô analítico do pipeline — consome discovery do PE, produz para SE SIM — handoff direto crítico no D4 pipeline order

Recomendação

Os 3 agentes pilotos são: product-engineer, software-architect, software-engineer.

Justificativa:

  • Os 3 cobrem o pipeline canônico definido em D4 (PE Discovery → architect → SE rec → PE Synthesis → SE impl) — validar este trio significa que o pipeline canônico está integralmente coberto por handoff verificável em v1.
  • Os 3 são os agentes invocados em todos os workflows seed (spec-refinement e tdd-cycle, ver public/workflows/), garantindo amostragem em produção em vez de exercício hipotético.
  • Produzem juntos 8 tipos distintos de output (5 do PE + 1 do arquiteto + 2 do SE) — variabilidade suficiente para estressar o schema sem big-bang.
  • É exatamente a sugestão do briefing — mas a verificação por inspeção confirma que essa escolha é tecnicamente correta, não apenas convencional.

Revisão considerada e rejeitada: trocar software-engineer por qa-engineer daria cobertura de red-phase + validation, mas perderia a validação do agente que mais frequentemente fecha tasks no workspace hoje (a auditoria orchestration 2026-05-15 lista software-engineer como o consumidor final do output_path bug — é o agente que mais se beneficia do handoff verificável).
