New alignment risks discovered during audit (NOT in original brief)

The brief asked me to surface any risks that I found during the audit beyond the three named gaps. Here are three.

Risk 1 — PR5-A4 fixture seeding may need r4 backfill output

Phase A task PR5-A4 (test_aggregator_sessions.py) seeds a small fixture to exercise list_sessions and get_session. If the fixture is hand-rolled it sidesteps r4 entirely — fine. But if any developer takes a shortcut and copies a small slice from the real ~/.dadaia/state/telemetry/telemetry.sqlite as the fixture seed, the slice must be taken after r4 PR4-09 executes the backfill — otherwise the slice carries 50 agent_name = NULL rows and the r5 unit test silently asserts the wrong invariant. Mitigation: PLAN already requires fixture be deterministic; reaffirm in CLOSURE that the fixture file tests/fixtures/telemetry/sessions_seeded.sqlite is hand-rolled, not sliced from live data.

Risk 2 — r5 Phase B closures need to coexist with r4 PR4-13's edits in api.py

The brief flagged the three-layer merge order on api.py (r4 PR4-13 tier → r5 Phase B new closures → r5 Phase D ?runtime= filter) but only as a Phase D rebase concern. The Phase B closures (render_api_sessions + render_api_session_detail per PR5-B1) are also at risk of merge conflict with r4 PR4-13's diff hunks — they all live in the same file. Mitigation: Phase B implementation must rebase on the latest release/panel-r4-v1 tip after r4 archives. Documented implicitly by Phase order (B comes after r4 archive) but not called out in TASKS. Consider adding a one-line rebase note to PR5-B1 in a future refinement if the merge proves painful.

Risk 3 — Phase D `runtime.js` load-order before `agents.js` / `workflows.js`

Phase C task PR5-C3 specifies that sessions.js falls back to literal "claude" if the Runtime global is not yet defined — graceful. But Phase D's PR5-D5 / PR5-D6 retrofit agents.js and workflows.js to subscribe to dadaia:runtime-change events emitted by runtime.js. If static.py registers runtime.js after agents.js / workflows.js in _ASSETS, the subscriber registration may run before the event source exists, missing the initial emission. PR5-D7 done-criterion already says "loads before agents.js, workflows.js, and sessions.js" — so this is covered, but the ordering invariant is asset-list-position-dependent and brittle. Mitigation: consider testing the load order with a small unit assertion on _ASSETS's element order in a future refinement; not blocking now.
