Phase 1 Discovery — Monitoramento de Agentes via dadaia-workspace Panel

Visão

Lema do operador: "Users will use the dadaia-workspace in its own environment. The dadaia-workspace panel must be secure. And the workspace resilient."

O dadaia-workspace panel hoje é uma superfície read-only de 3 abas (Servers, Memories, Agents & Workflows). A aba "Agents & Workflows" é um placeholder (features/panel/views/index.py:96-107). A release agent-monitoring-v1 evolui essa superfície para observabilidade real de agentes locais (Claude Code + Codex + opencode), consumindo apenas arquivos locais do operador — sem APIs remotas, sem dependências Node, sem ccusage.

Objetivos do release:

  • Separar as abas Agents e Workflows (hoje acopladas no nav).
  • Por agente: descrição, sessões trabalhadas, custos por sessão, tokens por tipo (input / cache_read / cache_creation / output), e custo total por Spec Context Project.
  • Por workflow: card descritivo + lista de agentes que o compõem.
  • Manter o bind 127.0.0.1:4999 e o caráter read-only do panel.
  • Princípio de supply chain: se conseguirmos tudo a partir dos providers locais, é a opção mais segura.

Identidade visual nova (paleta #9cddc8 #bfd8ad #ddd9ab #f7af63 #633d2e + logo rinoceronte monocromático) sai como spec paralela dadaia-workspace-brand-identity-v1 e não bloqueia agent-monitoring-v1 — fallback para tokens atuais do panel se ainda não estiver pronta.

Findings

  • Fonte primária Claude Code: ~/.claude/projects/-home-marco-workspace-dadaia/*.jsonl — um arquivo por sessão. Campos chave: sessionId, cwd, model, usage.{input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens}, entrypoint, gitBranch, timestamp. Sem campo cost.
  • Fonte primária Codex: ~/.codex/state_5.sqlite tabela threads.tokens_used (agregado, sem split in/out); history.jsonl para prompts. Codex usa thread_id, não correlaciona 1:1 com sessionId do Claude Code.
  • Sem Anthropic Admin API disponível: cálculo de custo precisa de tabela de preços versionada no repo (dadaia_workspace/features/telemetry/pricing.py proposto), com suite de testes para reproducibilidade do cálculo.
  • Panel atual é Python stdlib only (http.server.ThreadingHTTPServer, ~1.450 LOC). Qualquer dep nova precisa de justificativa forte do software-engineer.
  • Granularidade tem 4 dimensões úteis: sessão, agente, dia, Spec Context Project. Todas estão acessíveis nos jsonl (cwd identifica o Spec Context).
  • "Agente" não é trivial de definir nos jsonl: o campo subagent_type aparece quando o main thread invoca um sub-agente (ex: software-architect); para o main thread não há esse campo. Defaults registrados abaixo cobrem ambos os casos.
  • jsonl contém input verbatim do operador — risco de privacidade alto se o panel servir conteúdo bruto. Política: painel nunca serve texto de prompt/response.
  • Workflows não são agentes — são receitas (skills/plans) que orquestram agentes. Modelagem deve refletir isso (tabelas separadas).

Defaults registrados

O operador pediu para trabalhar sem pausas. Os 5 itens abaixo são defaults explícitos que substituem temporariamente uma rodada de dadaia-grill-me. Cada um é marcado DEFAULT — OPERATOR MAY OVERRIDE. Ficam vinculados à proposta de SPEC.md em Phase 3 e podem ser revistos no approval gate.

1. Granularidade DEFAULT — OPERATOR MAY OVERRIDE

  • Dimensões agregadas simultaneamente: (sessão, agente, dia, Spec Context Project). Todas computadas e expostas pelo backend.
  • UI default: por agente, com breakdown secundário por Spec Context Project.
  • Drill-down: clicar em um agente abre painel de sessões; clicar em sessão expõe metadados (sem conteúdo bruto). Datas filtráveis via faixa.
  • Justificativa: estas 4 dimensões saem de graça do parsing dos jsonl (campos sessionId, subagent_type ou entrypoint, timestamp, cwd). Reduzir agora amputaria visões úteis.

2. Retenção DEFAULT — OPERATOR MAY OVERRIDE

  • Raw events: 180 dias.
  • Agregados (por sessão, agente, dia, contexto): perpétuos.
  • Compactação: o reader processa jsonl in-place; SQLite local armazena agregados; jsonl raw permanece sob controle do provider (Claude Code / Codex), não copiamos.
  • Justificativa supply-chain: não introduzimos dependência de log-rotation externa (logrotate, journald). O panel só lê o que já existe. Retenção raw é limite de quanto processamos, não de quanto guardamos — Claude Code controla a vida do jsonl.

3. O que conta como "agente" DEFAULT — OPERATOR MAY OVERRIDE

  • Quando subagent_type está presente no evento jsonl: agente = subagent_type (ex: software-architect, frontend-engineer).
  • Quando ausente (main thread): agente = "claude (main)", com entrypoint exposto como dimensão secundária (cli vs vscode vs web).
  • Codex: agente = "codex (main)" sempre — Codex não expõe subagent_type. thread_id é o identificador de sessão.
  • opencode (se aparecer): agente = "opencode (main)" com mesma regra de fallback.
  • Workflows NÃO são agentes: são receitas (skills/plans) e têm modelagem independente — uma tabela workflows referencia os agentes que ela compõe, mas não acumula tokens.

4. Whitelist de entrypoints DEFAULT — OPERATOR MAY OVERRIDE

  • Sem filtro inicial: registramos todos os entrypoint encontrados nos jsonl (cli, vscode, web, etc.).
  • Exposto como facet/filter na UI: o operador filtra se quiser, mas dados completos ficam disponíveis.
  • Justificativa: cardinalidade baixa (≤ 5 valores observados); filtrar agora é prematuro e descarta informação que custa zero coletar.

5. Privacidade — política ESTRITA DEFAULT — OPERATOR MAY OVERRIDE

  • Painel NUNCA serve texto de prompt ou response. Sem exceção.
  • Campos permitidos via API: counts (token counts), sums (custos calculados), names (agent name, model name), sessionId, thread_id, timestamps, cwd, entrypoint, gitBranch.
  • Campos proibidos via API: content, text, qualquer fragmento de mensagem do operador ou resposta do modelo.
  • Sem endpoint /api/transcripts/<id>. Sem download de jsonl bruto via panel.
  • Justificativa: jsonl contém input verbatim do operador, incluindo potencialmente segredos digitados em prompts. Expor isso via HTTP local viola o lema "panel must be secure".

Restrições para especialistas (Phase 2)

Estas restrições são herdadas do plano aprovado e não negociáveis em Phase 2:

  1. Zero novas deps npm. Nada de ccusage, nada de Node.
  2. Minimizar deps Python. Hoje stdlib only no panel; qualquer adição precisa de justificativa explícita do software-engineer.
  3. Bind 127.0.0.1 permanece. Sem exposição remota nesta release.
  4. Transcripts são privados. Painel nunca serve conteúdo bruto de jsonl — apenas agregados (counts, sums, names). Sem /api/transcripts/<id>.
  5. Memory atomicity (SPEC-DOC-008). Diagramas e decisões vão para specs/memory/architecture.html; sem changelog inline.
  6. Naming SemVer não obrigatório (releases vintage ≤ 2026-05-17 isentas via SPEC-DOC-016) — agent-monitoring-v1 é OK.
  7. SQLite local é a proposta default. Especialistas podem desafiar com justificativa forte (ex: file-per-day jsonl agregado é suficiente). Decisão final do software-architect.
  8. Brand identity desacoplada. O spec de monitoring referencia tokens da dadaia-workspace-brand-identity-v1, mas não bloqueia se eles ainda não existirem (fallback aos tokens atuais).
  9. Reuso obrigatório: PanelService, ServerRegistryService, SpecContextService em features/panel/service.py. Novo TelemetryService deve seguir o mesmo padrão read-only com DI.
  10. PLAN.md ≤ 300 linhas (regra SPEC-DOC-005 ativa a partir de 2026-05-17).

Open questions for next grill-me iteration

Defaults acima são opiniões fundamentadas, mas as perguntas abaixo são verdadeiramente abertas e devem ir para dadaia-grill-me antes da redação final do SPEC.md em Phase 3:

  1. Política de retenção real: 180 dias é palpite. O operador prefere "tudo o que existe no disco hoje" (sem TTL no reader) ou um limite explícito? Impacta o tamanho do SQLite agregado.
  2. Tabela de preços — fonte da verdade: hard-coded no repo (auditável, requer PR pra atualizar) ou um JSON em ~/.dadaia/config/pricing.json editável pelo operador sem rebuild? Trade-off auditabilidade vs ergonomia.
  3. Inclusão de opencode: Phase 0 mapeou Claude Code + Codex. opencode tem dir de telemetria local (similar a ~/.opencode/)? Se sim, é escopo desta release ou de uma v1.1?
  4. Mapa de workflows: workflows vivem onde? .claude/skills/? specs/releases/*/PLAN.md? Precisamos do mapa fonte canônico para popular a aba Workflows — definição em Phase 3.
  5. Custo "por Spec Context Project": o jsonl tem cwd. Mapeamos cwd → spec_context via .dadaia/states/spec_contexts.json? Eventos com cwd fora de qualquer context (ex: /tmp) viram bucket "unassigned" ou são descartados?
  6. Alertas / thresholds: o painel deve apenas mostrar números, ou também alertar quando agente X excede $Y/dia? Default atual: só números. Confirmar ou expandir.
  7. Auth no panel local: hoje 127.0.0.1 sem auth. Com telemetria de custos disponível, mantém ou adiciona token local? devops-engineer deve avaliar threat model.

software-architect — tipo architecture

  • Onde mora o novo módulo: dadaia_workspace/features/telemetry/? Camadas: reader → store → aggregator → view com direção de dependência clara.
  • Schema SQLite proposto: tabelas sessions, events, agents, costs, contexts, workflows. Chaves primárias e índices.
  • Padrão de ingestão: polling (cron interno) vs watcher (inotify) vs lazy-on-request. Trade-offs e recomendação.
  • Atomicidade da escrita: WAL? lock? versionamento de migrations?
  • Avaliar se SQLite local é justificável ou se file-per-day jsonl agregado serve. Decisão final é sua.
  • Como o reader correlaciona cwd → spec_context: ler .dadaia/states/spec_contexts.json na ingestão ou em lookup-time.
  • Não mudar: read-only public-facing do panel; bind 127.0.0.1; reuso de PanelService.

frontend-engineer — tipo design

  • Split de Agents e Workflows em duas abas distintas no nav-tabs (views/index.py:69).
  • Layout de card de agente: header (nome + modelo dominante), mini-painel de sessões recentes, breakdown de custo por Spec Context, totais.
  • Layout de card de workflow: descrição + chips de agentes que compõem; sem números (workflows não acumulam tokens).
  • Contrato JSON consumido: definir formato de /api/agents e /api/workflows (campos exatos, paginação se aplicável). Cumprir restrição #4 (sem conteúdo bruto).
  • Integração com tokens da dadaia-workspace-brand-identity-v1 (paleta + rinoceronte); fallback aos tokens atuais se brand spec ainda não aprovada.
  • A11y: contraste mínimo WCAG AA, navegação por teclado nas abas.
  • Cumprir restrição #4: nenhum campo de conteúdo bruto em nenhum endpoint frontend.

software-engineer — tipo feasibility

  • Leitura segura de *.jsonl: file locking? incremental tail com checkpoint? recovery em arquivo truncado?
  • Parsing tolerante a versões: schema do jsonl pode mudar; usage.* campos podem aparecer/sumir.
  • Implementar dadaia_workspace/features/telemetry/pricing.py: tabela versionada (modelo → preço in/out/cache), suite de testes, função compute_cost(usage, model, when).
  • Strategy de schema migration do SQLite (qual ferramenta? versionamento via PRAGMA user_version?).
  • Listar dependências Python inevitáveis com justificativa (ex: aiosqlite só se assíncrono for justificado). Default: stdlib only.
  • Cobertura de Codex: sqlite3 stdlib + parsing de history.jsonl; mapeamento thread_id → agent="codex (main)".
  • Endpoint contracts no handler.py: respeitar regex dispatch existente; nunca servir content.

devops-engineer — tipo security

  • Threat model dos jsonl: contém input verbatim do operador, potencialmente segredos. Documentar superfície de ataque.
  • SQLite local deve ter chmod 600; localização (~/.dadaia/state/telemetry.sqlite?); owner = uid do operador.
  • Confirmar bind 127.0.0.1 permanece; sem auth adicional ou adicionar token local (open question #7).
  • DoS por jsonl gigante: políticas de read-budget (max bytes / max events por ciclo).
  • Rotação / compactação: o reader não copia raw — mas SQLite agregado precisa de política de tamanho máximo.
  • Supply-chain: revisar a lista de deps novas que software-engineer propuser; vetar tudo que não tiver justificativa forte.
  • Permissões cross-user: ~/.claude/projects/ é per-user. Garantir que o reader roda como o operador, não como root.
  • Logs do reader: sem PII, sem token counts por mensagem (apenas por sessão agregada).
