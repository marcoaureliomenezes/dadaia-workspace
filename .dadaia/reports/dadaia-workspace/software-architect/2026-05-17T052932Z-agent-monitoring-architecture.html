Phase 2 — Arquitetura para agent-monitoring-v1

Sumário executivo

A proposta arquitetural deste relatório segue cinco invariantes inegociáveis herdadas do plano e do Phase 1: zero deps npm, stdlib-first em Python, bind 127.0.0.1, transcripts privados, e memory atomicity SPEC-DOC-008. Dentro desses limites, recomendo:

  • Um novo feature top-level features/telemetry/ (não sub-módulo de panel), em pé de igualdade com features/panel/, features/server_registry/ e features/spec_context/.
  • Camadas explícitas reader → store → aggregator → view, com o PanelService orquestrando lookups read-only contra TelemetryService, mantendo o shape DI já estabelecido (features/panel/service.py:91-99).
  • Persistência em SQLite local com WAL mode, schema com 6 tabelas e dois índices únicos garantindo idempotência total.
  • Ingestão lazy on-request com checkpoint (sem cron, sem watcher, sem daemon) — menor complexidade operacional possível para um painel read-only.
  • Mapeamento cwd → spec_context em lookup-time, não em ingestão — protege contra renomear/desativar contextos sem reingerir histórico.

Decisões propostas

Tópico Decisão Justificativa Trade-off / risco aceito
D1. Localização do módulo PICK dadaia_workspace/features/telemetry/ (top-level peer de panel). REJECT features/panel/telemetry/; REJECT reuso de features/specs/. Telemetry é uma capability autônoma — ingere fontes externas (jsonl, sqlite Codex), tem ciclo de vida próprio (migrations, pricing) e é potencialmente consumida por mais de um surface (panel agora; dadaia doctor ou export amanhã). Aninhar em panel inverte a dependência (view ⇒ domain) e prende o store ao HTTP server. Mais uma feature top-level; PanelService precisa de DI explícito para TelemetryService. Custo trivial dado o padrão já existente.
D2. Direção de dependências features/panel → features/telemetry. Nunca o inverso. Telemetry só importa de core/ e stdlib. Mantém o panel como composition root da camada HTTP. Telemetry permanece testável sem subir servidor. Se um dia o panel migrar para outra superfície (CLI dadaia telemetry show), Telemetry continua intacto.
D3. Camadas internas reader → store → aggregator → view-adapter, 4 camadas. Reader produz RawEvent; store persiste idempotente; aggregator consulta agregados; view-adapter converte para o contrato JSON que handler.py serializa. CQRS-leve: escrita normalizada (eventos), leitura via views agregadas. Sem event-sourcing puro (overkill — não precisamos replay nem time-travel). Aggregator é uma camada SQL pura (não recompõe estado por replay). Se um dia precisarmos backfill com nova lógica, é re-ingestão completa do jsonl, não replay do store.
D4. Persistência PICK SQLite local com WAL. REJECT file-per-day JSON agregado. SQLite stdlib zero-dep, transações atômicas, índices, queries declarativas para 4 dimensões (sessão, agente, dia, contexto). File-per-day exige re-implementar group-by em Python — código que envelhece mal. Single-writer. Mitigado: WAL mode + reader é o único escritor; HTTP só lê. Sem concorrência de escrita real.
D5. Padrão de ingestão PICK Lazy on-request com checkpoint: ao receber GET /api/agents ou /api/workflows, TelemetryService.refresh() roda incremental tail (sourceset → offset persistido) com budget máximo e timeout, depois consulta agregados. REJECT cron / inotify / daemon. Painel é read-only sob demanda. Operador abre quando quer ver. Cron exige supervisor + monitoramento; inotify exige pyinotify (dep externa não justificável). Lazy mantém a arquitetura stdlib only e elimina superfície de falha em background. Primeira request "fria" do dia pode levar 500-1500ms se houver muitos jsonl atrasados. Mitigação: budget hard-cap (ex: 500 eventos por refresh; resto fica para a próxima request). Cache em memória do último resultado por 30s.
D6. Atomicidade e consistência PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; BEGIN IMMEDIATE envolvendo cada incremento de ingestão; uma transação por arquivo jsonl. Reader concorrente é proibido — lock de processo em ~/.dadaia/state/telemetry.lock via fcntl.flock. WAL permite leitura sem bloquear escrita. BEGIN IMMEDIATE previne write skew. Lock de processo elimina dupla ingestão se dois panels rodarem por engano. Se o painel crashar segurando o lock, flock libera com o fd; sem stale lock. Risco residual: 0.
D7. Idempotência da ingestão Identidade do evento: (source_kind, source_file, line_offset) + hash SHA-1 de uuid+timestamp+messageId (10 chars). Constraint UNIQUE em events(event_uid). Re-leitura de jsonl completo é no-op. jsonl pode ser truncado e reescrito (compactação do Claude Code); offset puro não basta. Hash composto blinda contra reordenação. Cálculo de hash em ingestão (CPU: ~50µs/evento). Aceitável.
D8. jsonl truncado / sessão em curso Reader trabalha com leitura linha-a-linha tolerante: linha JSON inválida ⇒ skip + log estruturado; não para a ingestão do arquivo. session.status = "open" enquanto o arquivo for o mais recente do diretório; "closed" caso contrário. Claude Code escreve jsonl com flushes; pode haver linha parcial no fim. Skip preserva forward progress. Última linha parcial fica perdida até ser reescrita completa. Aceitável (1 evento, sem custo associado finalizado).
D9. Mapeamento cwd → spec_context Lookup-time via SpecContextService.list_all(); matching por prefix descendente de path contra repo_path. Eventos órfãos (cwd fora de qualquer context ativo) recebem bucket unassigned — não são descartados. Lookup-time isola o histórico do ciclo de vida do registro de contextos: renomear, desativar, ou criar um context novo amanhã reclassifica eventos antigos sem reingestão. Prefix descendente cobre subdirs (cwd repos/foo/bar casa repo_path=repos/foo). Custo de lookup por evento agregado em query (não por evento individual). Bucket unassigned entra na UI como categoria explícita.
D10. Pricing table PICK Módulo Python versionado features/telemetry/pricing.py com dicionário literal {model: [PriceRow(effective_from, input, cache_read, cache_creation, output)]}. REJECT JSON config externo editável. Auditável via PR. Determinístico (test suite valida cálculo). JSON externo cria drift entre operadores e introduz superfície de edição que vaza para reproducibilidade. Atualizar preço exige PR + rebuild. Mitigação: UI mostra "preço usado: X (vigente desde Y)"; banner se preço > 90 dias. Operator pode contestar em Phase 3 grill-me se atrito for alto.
D11. TelemetryService shape Espelha PanelService (DI explícito, dataclasses read-only, sem side-effects em construtor). __init__(reader, store, aggregator, workspace_root, pricing_table). Métodos públicos: refresh(), list_agents(), list_workflows(), list_sessions_by_agent(name), costs_by_context(slug). Consistência arquitetural com PanelService, ServerRegistryService, SpecContextService. Permite reuso do mesmo padrão de testes (stubs por DI). Construtor com 5 args — testes em tests/features/telemetry/conftest.py devem fornecer factories.
D12. Workflows — fonte canônica PICK .claude/skills/ + .agents/skills/ (descoberta de SKILL.md com frontmatter name + description). REJECT specs/releases/*/PLAN.md e .dadaia/agentic/manifest.json. Skills são as receitas executáveis observadas pelo operador. PLAN.md é planejamento, não workflow. manifest.json é distribuição (mecânica de install), não capacidade. Skills têm frontmatter normalizado — leitura YAML stdlib trivial. Cobre Claude Code; opencode/Codex sem skills equivalentes ficam sem workflows mapeados — aceitável em v1 (workflows são "receitas para agentes", e a aba mostra apenas o que existe).
D13. Inclusão de opencode Defer para v1.1. v1 cobre Claude Code (jsonl) + Codex (sqlite + history.jsonl). Phase 0 mapeou Claude + Codex. opencode não tem provider de telemetria local documentado neste discovery. Forçar v1 amplia escopo sem ganho mensurável. Painel mostra duas fontes na v1. Se opencode aparecer, é adapter novo (features/telemetry/reader/opencode.py) — extensão Open/Closed compatível.
D14. Não-decisão (handoff) Auth no panel (Phase 1 open question #7) e DoS read-budget concreto: delegar a devops-engineer. Threat model não é domínio do architect; este report fixa apenas as superfícies arquiteturais (bind 127.0.0.1, sem auth adicional por enquanto). Se devops-engineer impuser auth token local, o handler ganha um middleware — não afeta camadas internas.

Schema SQLite (DDL inline, comentado)

-- ~/.dadaia/state/telemetry.sqlite — chmod 600, owner=uid do operador
-- PRAGMA configurados em conexão: journal_mode=WAL, synchronous=NORMAL, foreign_keys=ON
-- user_version: schema migrations via PRAGMA user_version (D6, D7)

PRAGMA user_version = 1;

-- =========================================================================
-- TABLE: source_files
-- Tracks every jsonl/sqlite source the reader has seen, with checkpoint
-- offset (D7 idempotência). One row per absolute path.
-- =========================================================================
CREATE TABLE IF NOT EXISTS source_files (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    path            TEXT    NOT NULL UNIQUE,        -- absolute path on disk
    kind            TEXT    NOT NULL,               -- 'claude_jsonl' | 'codex_sqlite' | 'codex_history'
    size_bytes      INTEGER NOT NULL DEFAULT 0,     -- last observed size
    line_offset     INTEGER NOT NULL DEFAULT 0,     -- next line to read (jsonl only)
    last_event_uid  TEXT,                            -- D7 idempotency anchor
    last_ingested_at TEXT   NOT NULL,                -- ISO 8601 UTC
    error_count     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_source_files_kind ON source_files(kind);

-- =========================================================================
-- TABLE: sessions
-- One row per Claude Code session (sessionId) or Codex thread (thread_id).
-- =========================================================================
CREATE TABLE IF NOT EXISTS sessions (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    external_id     TEXT    NOT NULL,               -- sessionId (Claude) or thread_id (Codex)
    provider        TEXT    NOT NULL,               -- 'claude' | 'codex' | 'opencode'
    entrypoint      TEXT,                           -- 'cli' | 'vscode' | 'web' | null
    cwd             TEXT,                           -- raw cwd from first event
    git_branch      TEXT,
    started_at      TEXT    NOT NULL,
    last_event_at   TEXT    NOT NULL,
    status          TEXT    NOT NULL DEFAULT 'closed',  -- 'open' | 'closed'
    source_file_id  INTEGER NOT NULL,
    FOREIGN KEY (source_file_id) REFERENCES source_files(id),
    UNIQUE (external_id, provider)                  -- idempotente cross-provider
);
CREATE INDEX IF NOT EXISTS idx_sessions_provider_started ON sessions(provider, started_at DESC);
CREATE INDEX IF NOT EXISTS idx_sessions_cwd ON sessions(cwd);

-- =========================================================================
-- TABLE: agents
-- Catalog of distinct agents observed. 'claude (main)', 'codex (main)',
-- 'software-architect', 'frontend-engineer', etc. (D3 default Phase 1).
-- =========================================================================
CREATE TABLE IF NOT EXISTS agents (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL UNIQUE,        -- subagent_type or ' (main)'
    provider        TEXT    NOT NULL,               -- 'claude' | 'codex' | 'opencode'
    is_subagent     INTEGER NOT NULL DEFAULT 0,     -- 1 when name came from subagent_type
    first_seen_at   TEXT    NOT NULL,
    last_seen_at    TEXT    NOT NULL
);

-- =========================================================================
-- TABLE: events
-- Append-only event log. ONE row per assistant message with usage data.
-- Idempotency anchor: event_uid (D7).
-- =========================================================================
CREATE TABLE IF NOT EXISTS events (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    event_uid       TEXT    NOT NULL UNIQUE,        -- D7: sha1(uuid||timestamp||messageId)[:20]
    session_id      INTEGER NOT NULL,
    agent_id        INTEGER NOT NULL,
    model           TEXT    NOT NULL,               -- 'claude-sonnet-4-6' etc.
    occurred_at     TEXT    NOT NULL,               -- ISO 8601 UTC
    tokens_input    INTEGER NOT NULL DEFAULT 0,
    tokens_cache_read INTEGER NOT NULL DEFAULT 0,
    tokens_cache_create INTEGER NOT NULL DEFAULT 0,
    tokens_output   INTEGER NOT NULL DEFAULT 0,
    -- pricing snapshot — computed at ingestion, denormalized for fast SUM().
    -- Recomputable from (model, occurred_at, pricing.py) — if pricing
    -- changes, run `dadaia telemetry recompute` (NOT in v1 scope; mention
    -- in PLAN as deferred capability).
    cost_micro_usd  INTEGER NOT NULL DEFAULT 0,     -- micro-USD (10^-6); avoids floats
    pricing_version TEXT    NOT NULL,               -- e.g. '2026-04-01' (effective_from of row used)
    FOREIGN KEY (session_id) REFERENCES sessions(id),
    FOREIGN KEY (agent_id)   REFERENCES agents(id)
);
CREATE INDEX IF NOT EXISTS idx_events_session ON events(session_id);
CREATE INDEX IF NOT EXISTS idx_events_agent_time ON events(agent_id, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_events_occurred ON events(occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_events_model ON events(model);

-- =========================================================================
-- TABLE: workflows
-- Discovered from .claude/skills/ and .agents/skills/ (D12).
-- Refreshed on the same lazy-on-request cycle as events (cheap; ~30 dirs).
-- =========================================================================
CREATE TABLE IF NOT EXISTS workflows (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL UNIQUE,        -- frontmatter 'name'
    source_path     TEXT    NOT NULL,               -- absolute path to SKILL.md
    description     TEXT,                           -- frontmatter 'description'
    apply_to        TEXT,                           -- frontmatter 'applyTo' (optional)
    discovered_at   TEXT    NOT NULL,
    last_seen_at    TEXT    NOT NULL                -- updated on every refresh
);

-- =========================================================================
-- TABLE: workflow_agents
-- Many-to-many: which agents a workflow declares to involve.
-- Populated by parsing the SKILL.md body for known agent names; in v1 this
-- is best-effort (substring match). Not a hard contract.
-- =========================================================================
CREATE TABLE IF NOT EXISTS workflow_agents (
    workflow_id     INTEGER NOT NULL,
    agent_id        INTEGER NOT NULL,
    PRIMARY KEY (workflow_id, agent_id),
    FOREIGN KEY (workflow_id) REFERENCES workflows(id) ON DELETE CASCADE,
    FOREIGN KEY (agent_id)    REFERENCES agents(id)
);

-- =========================================================================
-- INTENTIONALLY ABSENT
-- =========================================================================
-- NO table 'contexts' — Spec Contexts are owned by SpecContextService
-- (spec_contexts.json). We resolve cwd → context at QUERY time (D9), not at
-- ingestion. Duplicating context state here would break atomicity if the
-- operator renames or deactivates a context.
--
-- NO table 'costs' — costs are derived (SUM of events.cost_micro_usd grouped
-- by agent/session/context/day). Persisting pre-aggregated costs creates a
-- stale layer the moment pricing.py changes.
--
-- NO table 'event_content' or any column storing prompt/response text.
-- Privacy invariant (Phase 1 default #5): panel NEVER serves content.

Notas operacionais sobre o schema

  • Tamanho esperado: ~3-5 KB por sessão claude (apenas metadados de eventos). 1000 sessões ≈ 5 MB. Comporta anos de uso sem rotação.
  • Migrations: PRAGMA user_version incrementado por revisão do schema. store/migrations.py aplica migrate_to_v2.sql, migrate_to_v3.sql... idempotentes via IF NOT EXISTS e ALTER TABLE.
  • Pricing snapshot na events: cost_micro_usd + pricing_version denormalizados. Trade-off explícito: SUM rápido vs. necessidade de "recompute" se a tabela de preços corrigir um bug. v1 não inclui recompute (operador aceita ou abre task v1.1).
  • Sem floats: custos em micro-USD inteiro. SQLite floats em SUM degradam para multi-MB de eventos.

Findings (gaps vs. arquitetura declarada)

HIGH Composition root atual do panel não está preparado para injetar TelemetryService

Location: features/panel/server.py + features/panel/service.py:91-99

Issue: O construtor de PanelService aceita (registry, spec_context, workspace_root). Para inclusão de telemetry, é necessário um quarto argumento telemetry. O composition root (onde PanelService(...) é instanciado) precisa ser localizado e estendido.

Why it matters: Se a instanciação for ad-hoc, o software-engineer pode criar TelemetryService dentro de PanelService — violação de DIP e regressão do padrão estabelecido. Risco de divergência arquitetural já na primeira PR.

Trade-off if fixed: Uma assinatura a mais e uma chamada a mais no entrypoint. Custo mínimo, ganho de consistência alto.

Recommendation: Em PLAN.md, declarar como T-1 a localização explícita do composition root (provável features/panel/server.py ou CLI dadaia panel wrapper) e a regra: nenhum TelemetryService(...) instanciado fora desse ponto.

MEDIUM Handler regex-dispatch precisa de duas rotas novas sem regredir o contrato 404

Location: features/panel/handler.py:32-39 (_RAW_ROUTES) e :24-29 (_NOT_FOUND_BODY)

Issue: _RAW_ROUTES tem 6 entries hard-coded. _NOT_FOUND_BODY lista as rotas literalmente. Acrescentar /api/agents e /api/workflows exige editar ambos.

Why it matters: Drift entre rotas reais e mensagem 404 é o tipo de inconsistência que confunde desenvolvedores futuros. Hoje a mensagem está sincronizada — qualquer adição precisa preservar essa invariante.

Trade-off if fixed: Manter sincronizado manualmente, ou refatorar _NOT_FOUND_BODY para ser gerado a partir de _RAW_ROUTES. O refator é trivial mas fora do escopo desta release.

Recommendation: Em TASKS.md, ter uma task explícita "atualizar _NOT_FOUND_BODY com /api/agents e /api/workflows" — não delegar para o software-engineer descobrir.

MEDIUM Privacidade exige whitelist de campos no aggregator, não só no handler

Location: camadas aggregator/queries.py → service.py → views

Issue: Restrição #4 (transcripts privados) é uma regra de arquitetura, não só de view. Se o aggregator devolver dataclasses com campos potencialmente sensíveis (ex: cwd contendo path absoluto do operador), a tentação de exibir cresce com o tempo.

Why it matters: "Built on stale layers" — uma feature futura pode adicionar campo content em dataclass e o handler vazar sem revisão.

Trade-off if fixed: Dataclasses específicas para cada endpoint (AgentSummary, WorkflowSummary, SessionSummary) em vez de dataclass única "rica". Mais classes, contratos mais explícitos.

Recommendation: Declarar na arquitetura: nenhuma dataclass de telemetry contém campos content, text, prompt, response, thinking. Constraint estática a ser checada por teste (grep nos imports).

LOW Lock file location must avoid ~/.dadaia/state/ race with CLI

Location: ~/.dadaia/state/telemetry.lock proposto

Issue: ~/.dadaia/state/ contém arquivos JSON da CLI (primary_context.json, spec_contexts.json, server_registry.json). Colocar lock junto cria possível confusão de propriedade.

Recommendation: Usar ~/.dadaia/state/telemetry/telemetry.lock e ~/.dadaia/state/telemetry/telemetry.sqlite num subdir dedicado. Custo zero, clareza alta.

Contestação ao SQLite — file-per-day JSON agregado

Avaliado conforme restrição #7 do plano. Rejeitado. Tabela de trade-offs:

CritérioSQLite localFile-per-day JSON agregado
