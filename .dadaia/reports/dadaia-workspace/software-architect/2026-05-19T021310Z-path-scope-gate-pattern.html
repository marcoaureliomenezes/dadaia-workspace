Path-Scope Gate — Runtime Agent-Detection & Fail-Open Pattern

This report is the architect consult required by SPEC §FR2.2, NFR3, Risk R2 and TASKS AGT-r2-12. It selects ONE concrete runtime agent-detection mechanism for the path-scope check that software-engineer will land in dadaia_workspace/public/scripts/sdd-spec-gate.sh under AGT-r2-19, and specifies the unit-test seams that AGT-r2-20 must cover.

The report is design-only. It does NOT contain gate code. The gate code lives in the v3 hook script (already on disk at dadaia_workspace/public/scripts/sdd-spec-gate.sh); the path-scope step is appended after the existing TASKS-marker step and BEFORE the script's final exit, per TASKS AGT-r2-19 wording.

1. Context

Release agents-r2-v1 activates paths: as a runtime-enforced field in every agent's frontmatter (SPEC §FR2.1 — 16 agents, each with a write_allowlist glob list). The sdd-spec-gate.sh PreToolUse hook receives, for every Write/Edit/MultiEdit tool call, a JSON payload on stdin describing the tool name and target file path. Today the hook gates on:

  1. Memory-atomicity (writes to specs/memory/** require ACTIVE.md phase=CLOSURE);
  2. Archive read-only (writes to specs/_archive/** always blocked);
  3. Meta-edits passthrough (writes to TASKS.md / PLAN.md / SPEC.md / CLOSURE.md / ACTIVE.md / backlog/*.md always allowed);
  4. Production-path gating (writes under services/, repos/<primary_slug>/ etc. require a [-] marker in some TASKS.md).

Release r2 adds step 5: path-scope check — reject the write if the active agent's write_allowlist does not match the target path. To do that the gate must, at runtime, answer ONE question:

Which agent persona is invoking this tool right now?

Risk R2 (SPEC §7) flagged that Claude Code, Codex, and OpenCode do not agree on how to surface agent identity into a hook. R5 flagged that an over-eager gate would block legitimate human top-level invocations. NFR3 hardens the rule: when the agent persona is undetectable, the gate MUST fail open.

2. Options weighed

Option Mechanism Trade-offs
A — Env var only Single env var (e.g. DADAIA_AGENT_PERSONA) is exported by every harness before dispatching a sub-agent invocation. Hook reads $DADAIA_AGENT_PERSONA from its own process environment. simple requires harness cooperation
Pros: shell-readable in 1 line; no JSON parsing branch; harness-independent at the gate level. Cons: each harness must learn to set it. Claude Code does not propagate env vars into sub-agent processes by default — this becomes a per-harness shim. If the shim is missing, the gate fails open everywhere (effectively disables path-scope).
B — PreToolUse payload field only Hook reads tool_input.agent or _meta.agent_persona from the JSON payload on stdin. Each harness is responsible for stamping the field. survives env-var sandboxing harness-specific field name
Pros: payload always flows through the hook regardless of process isolation; Claude Code's hook payload already carries tool_input. Cons: there is no cross-harness contract today for "agent persona" inside the payload — each harness would need a separate parsing branch (more code, more drift). Codex and OpenCode do not currently emit this field at all.
C — Per-harness heuristic only Probe runtime files that each harness writes for its own bookkeeping (e.g. ~/.claude/projects/<hash>/sessions/<sid>.jsonl) and parse the active agent from the last assistant turn. brittle, undocumented contract
Pros: zero changes to harnesses. Cons: parses an internal log file with no stability guarantees; differs per OS; can race with the harness writing the log; would have to be rewritten on every Claude Code minor release. Operational liability is unacceptable for a gate that must add < 50 ms (NFR2).
D — Layered chain (env → payload → fail-open) Hook tries sources in fixed priority order, falling through on absence:
  1. DADAIA_AGENT_PERSONA env var (neutral, lib-defined)
  2. Harness-specific env var (CLAUDE_AGENT_PERSONA / CODEX_AGENT_PERSONA / OPENCODE_AGENT_PERSONA) — same value, different name for harness-side discoverability
  3. JSON payload field tool_input._meta.agent_persona (best effort — only present in harnesses that stamp it)
  4. Nothing found → fail open with single warning line.
 harness-agnostic forward-compatible unit-testable
Pros: one neutral env var is the contract; harness-specific names are documented aliases (no behaviour difference); payload path future-proofs against harnesses that move to JSON-only injection (Anthropic has hinted at this); fail-open is explicit, logged, and reachable by test. Cons: requires shim documentation in each harness's AGENTS.md section (operator-facing). The shim is small — one line in the agent dispatcher's wrapper.
Decision — Option D (layered chain). The path-scope check resolves the active agent persona by trying, in fixed order: (1) DADAIA_AGENT_PERSONA, (2) harness-specific env var, (3) JSON payload field, (4) fail-open. The contract is documented per harness in data/AGENTS.md (the lib-shipped guardrail doc, rewritten in AGT-r2-33); the path-scope gate itself remains harness-agnostic.

3. Detection contract per harness

Same value semantics in all three harnesses: the persona is the agent's name: from frontmatter (e.g. software-engineer, code-reviewer). The gate matches that name against the paths.write_allowlist block of the agent file by the same agent reader used in tests/unit/features/agents/test_agent_reader.py.

Harness Primary surface Operator-facing setup Status today
claude-code Env var. Claude Code spawns its hook process with the user's environment plus the JSON payload on stdin. The agent dispatcher (sub-agent runner) sets DADAIA_AGENT_PERSONA before tool invocation. No operator action under normal use — Claude Code's sub-agent runner sets the var automatically. For top-level human invocations the var is unset → fail open by design (NFR3). runner shim required
The shim is a 1-line export in the wrapper that Claude Code uses to invoke each agent persona. Documented in data/AGENTS.md §"Agent persona contract". Until the shim lands, every claude-code invocation fails open with the documented warning — same as Codex / OpenCode in the interim.
codex Env var CODEX_AGENT_PERSONA. Codex spawns hooks via .codex/hooks.json with the parent process env inherited. Operator sets the var via the persona wrapper (a thin shell function exported in the operator's shell rc) before launching Codex sessions for a specific persona. Top-level Codex sessions where the var is unset fail open. shim required
opencode Env var OPENCODE_AGENT_PERSONA. OpenCode hooks run in the same process env as the editor. Same as Codex. shim required

All three harnesses ALSO accept DADAIA_AGENT_PERSONA as the priority-1 source. The harness-specific aliases exist only so a harness-curious operator can trace which harness is involved at a glance — semantically they are identical.

JSON payload fallback (priority 3)

When future harnesses stamp the persona in the tool-input payload (current Claude Code internal API has tool_input._meta reserved but not standardised), the gate reads tool_input._meta.agent_persona from the JSON on stdin using the same one-shot Python invocation already used in the gate to parse tool_name and file_path — one extra JSON-load, < 5 ms. If the field is absent or non-string, the gate moves to priority 4 (fail open).

4. Cache strategy

Each PreToolUse invocation spawns a fresh shell process — the gate cannot rely on in-memory state across invocations. The cache scope is therefore per-invocation only, not per-turn.

Cache decision — per-invocation, in-process only. Within a single hook process, the gate resolves the active agent's allowlist exactly once (one read of the agent's frontmatter file) and uses the result for whatever matching the script does in that invocation. There is no persistent cache file. There is no inter-process cache.

Why no cross-invocation cache

Cache layer Verdict Reason
In-memory (per-invocation) use The path-scope step runs after the existing memory/archive/meta-edit branches. Inside that one branch, the gate reads ONE frontmatter file and ONE glob list. Cost: one bash read + one Python YAML/key parse — well under NFR2's 50 ms budget without any cross-invocation persistence.
File-backed cache (e.g. /tmp/sdd-gate-cache.json) do not introduce Adds invalidation surface (file edit to agents/*.md must invalidate the cache); adds concurrency hazard (parallel hook processes writing the same cache file); buys nothing — each invocation reads ONE small YAML block.
Long-running daemon out of scope Out of proportion to the problem. The gate is a 200-line shell script with one Python sub-invocation; a daemon would be 100× the operational surface.

Per-invocation cache footprint (informative)

The gate's path-scope step touches, per invocation, these files exactly once:

  1. The persona's agent file at <workspace>/dadaia_workspace/public/agents/<persona>.md (or the installed projection at .claude/agents/<persona>.md — the gate prefers the public source as the canonical truth, with the projection as fallback). Reads only the frontmatter block (the YAML between the leading --- fences); aborts the read at the first non-frontmatter line.
  2. The JSON payload on stdin — already cached in $TMP by the pre-existing gate code (cat > "$TMP" line). The path-scope step reuses $TMP; no second stdin read.

Result: 1 frontmatter read + reuse of existing stdin cache. Single agent file read per hook invocation is the entire per-invocation cost.

5. Fail-open behaviour (NFR3 / FR2.4)

When NONE of the four resolution paths yields an agent persona, the gate MUST allow the write and emit a single warning line to /tmp/sdd-gate.log. The warning includes enough information to diagnose missing-shim or harness-issue scenarios, but never enough to mask a real path-scope violation if a persona later appears.

5.1 Log format (literal)

The fail-open log line follows the existing gate log format, with an explicit FAIL-OPEN tag and the surfaces that were probed:

[2026-05-19T02:13:10+00:00] sdd-gate: FAIL-OPEN path-scope: no agent persona detected (env=unset payload=unset) tool=<TOOL> path=<FPATH>

Specifications:

  • Timestamp prefix: ISO-8601 with timezone offset, matching the existing _log helper in the gate ($(date -Iseconds)).
  • Prefix tag: sdd-gate: (matches existing helper).
  • Severity tag: FAIL-OPEN (all caps, single token, distinct from BLOCKED and the bare informational lines so a grep can filter them).
  • Reason tag: path-scope: (allows future FAIL-OPEN memory-gate: or similar without ambiguity).
  • Probe summary: env=<set|unset> payload=<set|unset>. Two literals only — do NOT log the value of the env var (it would leak operator-side internals if the var were ever set to something unexpected).
  • Context fields: tool=<TOOL> and path=<FPATH>, identical to the existing informational log lines so a post-incident operator can correlate.
  • Exactly one line per fail-open event. The gate must not repeat the line, even if multiple resolution paths fail in the same invocation.

5.2 Decision payload (literal)

Even though Claude Code's PreToolUse contract treats a silent exit 0 as implicit-allow, the gate emits the explicit JSON token for symmetry with the _block helper and to support Codex's stricter parser:

{"decision":"allow"}

Emitted on stdout. exit 0. No further processing.

5.3 Log retention

The log file /tmp/sdd-gate.log already exists, lives under /tmp/, and is therefore auto-purged on reboot. The path-scope branch inherits this retention; no rotation is introduced. The gate MUST NOT attempt to rotate, truncate, or chmod the log — the file is created with the default user-process umask when first written by _log. Operators who want longer retention symlink /tmp/sdd-gate.log to a persistent path outside /tmp/; that is operator policy, not gate concern.

Anti-amplification rule. A fail-open event is logged exactly once per hook invocation, never inside a loop. The path-scope step's first action after resolution failure is the _log call; subsequent code paths inside the same hook invocation MUST NOT re-log the same fail-open. This prevents the log from filling under bursty editor workloads.

6. Error format on block (FR2.3)

When the gate detects a path-scope mismatch (persona resolved, allowlist does NOT match target path), the block payload is the literal:

{"decision":"block","reason":"[PATH SCOPE ERROR] agent <X> cannot write to <path>. write_allowlist: <list>."}

Substitution rules:

Token Substitution Notes
<X> Persona name from the resolved env var or payload field, e.g. code-reviewer. No quotes. No leading @. Matches the agent file's name: frontmatter value verbatim.
<path> The target file path, absolute, as surfaced by the existing gate's FPATH variable. Already absolute by the time the path-scope step runs — the gate prefixes $WS/ to relative paths earlier.
<list> Comma-separated render of the agent's paths.write_allowlist globs, in the order they appear in frontmatter. No surrounding brackets. No trailing comma. Example: .dadaia/reports/<ctx>/code-reviewer/**. The literal <ctx> is left unresolved in the error message — the operator reads it as the templated value that matched their context.

The reason string must be JSON-escaped exactly as the existing _block helper escapes its argument (it uses printf '{"decision":"block","reason":"%s"}' "$1"; quotes inside the reason string must be pre-escaped by the caller). The path-scope branch passes the literal string above with no embedded double quotes — the angle-bracket tokens are not JSON-significant.

Exit 0 after emission (matches existing _block behaviour).

7. Position in the gate's existing control flow

The path-scope step is the FIFTH gate, appended after the meta-edit passthrough and before the production-path / TASKS-marker step:

Order Step Outcome
1Parse $TOOL — non-write tool → exit 0silent allow
2Parse $FPATH — empty → exit 0silent allow
3RULE A — memory atomicityblock or allow + exit 0
4RULE B — archive read-onlyblock or fall through
5Meta-edit allow-listallow + exit 0 or fall through
6RULE D — path-scope (NEW)block | fail-open | fall through
7Production-path classification + TASKS-markerblock or allow

Ordering rationale:

  • After memory atomicity (step 3): memory-gate is a strictly tighter rule (only product-engineer in CLOSURE phase). It must fire first so that even a misconfigured persona allowlist cannot accidentally allow a memory edit in TASKS phase. Path-scope is the second line of defence, not the first.
  • After archive read-only (step 4): same logic — archive is universally read-only.
  • After meta-edit passthrough (step 5): meta-edits (TASKS.md, SPEC.md, etc.) are explicitly path-scope-exempt because the task-marker protocol requires PE / SE / PM / any agent currently working a task to update TASKS.md. Putting path-scope after this branch means agents do not need specs/releases/** in their allowlist just to flip their own task marker.
  • Before production-path classification (step 7): a path-scope mismatch on a write to e.g. repos/<primary>/foo.py by code-reviewer should be rejected with the path-scope error (more diagnostic) rather than with the generic "no IN PROGRESS marker" error (less diagnostic).

Fail-open inside the step

Inside the path-scope branch, fail-open is an INTRA-step fall-through: the branch logs the FAIL-OPEN line, emits {"decision":"allow"} on stdout, and exits 0. It does NOT fall through to step 7 (production-path / TASKS-marker). This preserves the gate's existing top-level human invocation behaviour: a top-level human edit with no persona resolved already passes today's gate via the TASKS-marker logic (a top-level human typically has flipped a [-]); but a top-level human editing without any task marker would be blocked at step 7. The new step 6 fail-open shortcut deliberately bypasses step 7 for human invocations — this is the SPEC §FR2.4 wording ("preserves human-driven invocations").

Trade-off explicitly accepted. Fail-open at step 6 means a human invocation without an active [-] task marker now slips past the TASKS-marker gate that previously caught it. The gate becomes more permissive for humans (intended) and identical for agents (intended). The operator-facing consequence: top-level human edits no longer require a task marker. This matches the operator's stated direction (SPEC §FR2.4: "preserves human-driven invocations") and is documented in data/AGENTS.md §"Path-scope gate behaviour".

8. Resolution algorithm (specification, not implementation)

This section is the contract that AGT-r2-19 implements. It is described in pseudocode-grade language; this is not the gate code — the gate code is software-engineer's deliverable. 

function resolve_persona(payload_json):
    # Priority 1 — neutral env var
    if env DADAIA_AGENT_PERSONA is set and non-empty:
        return (env DADAIA_AGENT_PERSONA, source="env-neutral")

    # Priority 2 — harness-specific env vars (tried in fixed order)
    for var in [CLAUDE_AGENT_PERSONA, CODEX_AGENT_PERSONA, OPENCODE_AGENT_PERSONA]:
        if env var is set and non-empty:
            return (env var, source="env-harness")

    # Priority 3 — JSON payload field
    persona = json_get(payload_json, "tool_input._meta.agent_persona")
    if persona is non-empty string:
        return (persona, source="payload")

    # Priority 4 — fail open
    return (None, source="fail-open")

function path_scope_check(persona, target_path):
    if persona is None:
        log("FAIL-OPEN path-scope: ...")
        emit {"decision":"allow"}
        exit 0

    allowlist = read_frontmatter_write_allowlist(
        dadaia_workspace/public/agents/<persona>.md
    )
    if allowlist is None:  # agent file missing or no paths block
        log("FAIL-OPEN path-scope: agent persona <persona> has no paths block")
        emit {"decision":"allow"}
        exit 0

    if any glob in allowlist matches target_path:
        log("allowed — path-scope ok: persona=<persona> path=<path>")
        return  # fall through to step 7

    emit {"decision":"block",
          "reason":"[PATH SCOPE ERROR] agent <persona> cannot write to <target_path>. write_allowlist: <list>."}
    exit 0

Glob-matching contract:

  • Globs are evaluated relative to WORKSPACE_ROOT (the gate's existing $WS).
  • The match is a recursive shell-style glob (** matches any number of path segments, * matches a single segment). Software-engineer implements this with bash's compgen or a Python one-liner; the detail is implementation, not contract.
  • If the target path is outside WORKSPACE_ROOT (an unlikely edge), the gate fails open with a warning — never blocks. This protects against path edge cases (symlinks, /tmp/, etc.) without a special case in the allowlist schema.

11. Risks introduced by this decision

Risk Severity Mitigation
Shim absence renders the gate ineffective. Until each harness sets DADAIA_AGENT_PERSONA in its sub-agent runner, every agent invocation fails open with the documented warning — the path-scope protection is effectively dormant. HIGH Document the one-line shim in data/AGENTS.md §"Agent persona contract" (added by AGT-r2-33). Operator's PM has the responsibility to set the var when dispatching. The release ships the gate ready to enforce; enforcement activates when shim lands. This is an explicit trade-off vs Option C (harness-internal heuristic) which would have been immediately active but unstable.
Persona spoofing. Any agent that can set its own env var could declare itself code-reviewer and bypass the software-engineer allowlist by impersonation. MEDIUM Path-scope gate is a guardrail against accidental drift, not a security boundary. The threat model for this release does not include malicious agents inside the runner. If that threat model changes, the persona signal moves out of env vars into a runner-signed token in the JSON payload (future release; explicitly out of scope per NS1).
Glob mismatch ambiguity. An agent's allowlist uses <ctx> templating (e.g. .dadaia/reports/<ctx>/code-reviewer/**). If the gate template-substitutes <ctx> incorrectly (e.g. uses repo slug when the active context is the workspace itself), every write looks like a path-scope mismatch. MEDIUM The gate resolves <ctx> from .dadaia/states/primary_context.json — the same source the existing gate uses for $PRIMARY_SLUG / $PRIMARY_SPECS. AGT-r2-20 T1 + T2 use the actual <ctx> resolution path so any drift surfaces as a test failure. R5 (already declared) covers the post-merge log-monitoring response.
Frontmatter parse error. If an agent file has malformed YAML frontmatter (missing trailing ---, mixed indentation), the gate's frontmatter reader fails. The gate must fail open in that case, not block. LOW Algorithm §8 specifies: "read_frontmatter_write_allowlist returns None on any parse error". The None branch fails open with a distinct log line (FAIL-OPEN path-scope: agent persona <persona> frontmatter parse error). Test T6 covers the "no paths: block" variant; AGT-r2-20 may extend with a "malformed frontmatter" variant if SE deems it worth the fixture overhead. Otherwise, the broken-frontmatter case is caught by the existing test_agent_reader.py CI.
