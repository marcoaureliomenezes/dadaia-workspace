## 3. Proposed: where does `specs/hotfix/` fit?

### Option A — Parallel to releases: `specs/hotfix/<version>/`

```
specs/
├── releases/
│   ├── ACTIVE.md
│   └── <release-id>/
├── hotfix/
│   ├── ACTIVE.md (?) or shared ACTIVE.md
│   └── <hotfix-id>/ (e.g. v1.2.1)
│       └── HOTFIX.md (or SPEC/TASKS/CLOSURE depending on §4)
└── _archive/
    ├── releases/<id>/
    └── hotfixes/<id>/
```

| Aspect | Cost |
|---|---|
| Gate complexity | LOW — Rule C grep adds one more path: `specs/hotfix/*/TASKS.md` (or single-file `HOTFIX.md`). Rule A unchanged (memory remains untouched outside CLOSURE). Rule B extends to `_archive/hotfixes/*`. |
| Doctor complexity | MEDIUM — new check `SPEC-DOC-013` (hotfix structure), extend `_check_no_orphan_specs` whitelist, extend `_check_archive_closures` to also scan `_archive/hotfixes/`. ~3 new checks or 3 extensions. |
| Agent cognitive load | LOW — `specs/hotfix/` is a sibling of `specs/releases/`; the mental model "releases is planned work, hotfix is reactive work" maps to two visible trees. |
| Navigation | GOOD — humans see two parallel concerns immediately; archive history is preserved as `_archive/hotfixes/` mirroring `_archive/releases/`. |
| ACTIVE.md impact | Forces decision: one ACTIVE.md for both (dual pointer) or one ACTIVE.md per tree (two files). See §5. |

### Option B — Nested under release: `specs/releases/<version>/hotfixes/<patch>/`

```
specs/releases/
├── ACTIVE.md
└── workspace-panel-v1.2.0/
    ├── SPEC.md
    ├── PLAN.md
    ├── TASKS.md
    ├── CLOSURE.md
    └── hotfixes/
        ├── v1.2.1/
        │   └── HOTFIX.md
        └── v1.2.2/
            └── HOTFIX.md
```

| Aspect | Cost |
|---|---|
| Gate complexity | HIGH — Rule A pattern stays clean but Rule C grep must traverse nested `releases/*/hotfixes/*/TASKS.md`; the existing `grep -r ... releases/*/TASKS.md` would need either `--include="TASKS.md"` (which already exists at L166) plus careful exclusion of CLOSED hotfixes. Increases failure surface of a fail-open shell script. |
| Doctor complexity | HIGH — `_check_no_orphan_specs` whitelist breaks because hotfix is technically nested; `_check_archive_closures` would have to walk into closed-release subtrees to find hotfixes; PLAN line-limit may apply to hotfix PLAN that may not need a PLAN at all. |
| Agent cognitive load | HIGH — "what release is the active one" answer suddenly depends on whether you mean "the release whose hotfix is active". Memory model gets blurred. |
| Navigation | POOR — humans must descend into a release dir to find hotfixes; once a release is archived, its hotfixes become invisible in the active tree but still semantically meaningful (the production binary IS at v1.2.x). |
| ACTIVE.md impact | Demands a 3-key ACTIVE.md or path-style pointer. |

### Option C — Hotfix is a phase, not a new folder

```
specs/releases/
├── ACTIVE.md (phase=HOTFIX_DISCOVERY or HOTFIX_IMPLEMENTATION)
└── workspace-panel-v1.2.0/
    ├── SPEC.md          ← original
    ├── PLAN.md
    ├── TASKS.md         ← can grow with [hotfix] tasks appended
    ├── CLOSURE.md       ← already written; or amended (violates atomicity!)
    └── HOTFIX-<patch>.md (?)
```

| Aspect | Cost |
|---|---|
| Gate complexity | LOWEST — no new paths, only new phase names |
| Doctor complexity | LOW |
| Agent cognitive load | HIGH and broken — release lifecycle is `... → CLOSURE → ARCHIVED`. Allowing the phase to go BACK to `HOTFIX_*` on an archived release violates the existing invariant "archive is read-only" (Rule B). Either we break Rule B or we leave the release in `IMPLEMENTATION` indefinitely. Both options break invariants the operator deliberately built. |
| Navigation | POOR — archived release can never be truly "done" |
| Memory atomicity | BROKEN — if a hotfix triggers memory update (very common: bug exposed an undocumented behavior), memory CLOSURE-write would need to happen on a release already ARCHIVED. |

### Recommendation: Option A (parallel tree)

Option A is strongly recommended. Justification anchored in the existing code:

1. **Rule B already encodes "archived = frozen"** (`sdd-spec-gate.sh` L108–112 with no phase exception). Option C requires either weakening Rule B or accepting "permanent IMPLEMENTATION" — both regress observable invariants.
2. **Doctor `_check_no_orphan_specs`** (L582–602) is a path-prefix whitelist. Option A extends the whitelist by one entry (`hotfix/`); Option B requires structural rewrites.
3. **Memory atomicity** (Rule A, `sdd-spec-gate.sh` L96–104) is the most important invariant in the workspace. A hotfix that uncovers a fact the memory got wrong must be able to write memory in its OWN closure — not in the closure of a 6-months-old archived release. This forces Option A.
4. **Symmetric `_archive/hotfixes/<id>/`** preserves the existing archival pattern without inventing a new shape.

Cost paid: ACTIVE.md must support concurrency between a release-in-flight and a hotfix-in-flight (see §5).

## 4. Hotfix data model

A hotfix is a **reactive, time-pressured patch**. The data model must be lighter than a full release to avoid the data model fighting the workflow's nature.

### 4.1 Required artifacts — three live options

| Variant | Artifacts | When appropriate |
|---|---|---|
| **Single-file** | `HOTFIX.md` only | When the bug + fix + validation fit on one page. Most hotfixes. |
| **Minimal-triple** | `HOTFIX.md` + `TASKS.md` + `CLOSURE.md` (no SPEC, no PLAN) | When the fix needs ≥3 tasks for parallel implementer work. |
| **Full** | `SPEC.md` + `PLAN.md` + `TASKS.md` + `CLOSURE.md` | When the hotfix grew into something resembling a small release — should be re-classified as a MINOR or MAJOR release instead. Discourage. |

**Recommendation:** standardize on **minimal-triple**. Rationale:
- `HOTFIX.md` carries the SPEC role (what changed, why, evidence) but stays small (`<200` lines).
- `TASKS.md` preserves the `[ ]`/`[-]`/`[x]` mechanism that Rule C of the gate already relies on. Without TASKS.md, the gate has no way to authorize a production write — and weakening the gate for hotfixes would create the very "spec-light backdoor" risk in §11.
- `CLOSURE.md` preserves doctor check `SPEC-DOC-006` symmetry (evidence triple, drifts, memory updates).
- `SPEC` and `PLAN` are skipped because (a) the hotfix is its own SPEC, (b) PLAN line-limit (300) is overkill for a fix that should be ≤1 day of work.

### 4.2 Minimal vs full Documentation

`HOTFIX.md` required sections (modeled on `CLOSURE.md` but inverted — diagnosis-first):

| Section | Purpose | Mirror |
|---|---|---|
| `## Incident` | What broke; how it was detected | new |
| `## Root cause` | Mechanical explanation; file:line if possible | new |
| `## Fix` | What changes; blast radius | mirrors release SPEC's "Deltas" |
| `## Patches release` | Which release-id this hotfix patches (back-link) | new; see §4.4 |
| `## Validation` | How the fix was verified — same `{description, command, evidence}` triple format as CLOSURE | mirrors `_check_archive_closures` |
| `## Memory updates` | Empty if the hotfix doesn't touch product memory; otherwise list of `memory/*.html` files | mirrors release CLOSURE.md `## Memory updates` |

### 4.3 Status field

A hotfix moves fast — the `Draft → Em revisão → Aprovado` ladder is overkill for a 2-hour incident response. **Recommendation:** keep the canonical `CANONICAL_STATUS` set (`doctor.py` L34) and require `**Status:** Aprovado` only on `HOTFIX.md` (since it serves both SPEC and CLOSURE roles). For `TASKS.md` and `CLOSURE.md`, the canonical status applies as today.

### 4.4 Link back to the release it patches

`HOTFIX.md` must declare `## Patches release` with the release-id string. Doctor adds a check: target id must resolve to either `_archive/releases/<id>/` or `releases/<id>/`. This is the cross-reference that gives the SemVer model meaning — see §5/§10.

## 5. ACTIVE.md format alternatives

The biggest decision in this design. Three alternatives:

### Option α — Single pointer (only release OR only hotfix active)

```
release: agent-sdd-alignment-v1
phase: TASKS
```

If a hotfix is started while a release is in flight, the operator must pause the release: replace the active pointer, work the hotfix, then restore the original release pointer.

Pros: zero schema change; doctor and gate need no extension.

Cons: A real hotfix is exactly the case where a regular release **cannot be paused** to wait — the bug is in production NOW. Forcing serial activation defeats the purpose. Also: which agent is responsible for restoring the original pointer? Today nothing tracks this.

### Option β — Dual pointer (both active simultaneously)

```
release: agent-sdd-alignment-v1
phase: TASKS
hotfix: v1.2.1
hotfix_phase: HOTFIX_IMPLEMENTATION
```

Pros: Both tracks can run truly in parallel. Reflects the operational reality (you patch prod while you keep building MINOR work on develop).

Cons:
- `doctor.py::_read_active_md` (L189–206) currently parses exactly 2 keys; needs a 4-key variant. Backward compat: if `hotfix:` line absent, treat as no hotfix in flight.
- Rule A becomes ambiguous: which CLOSURE phase unlocks memory? **Decision rule needed**: memory writes allowed if `phase=CLOSURE` (release closure) OR `hotfix_phase=HOTFIX_CLOSURE`. The gate `case` statement needs OR logic.
- Rule C becomes harder: which `TASKS.md` does the gate grep? If both have `[-]` tasks, fine; if a contributor working on the release accidentally edits a hotfix file, the gate might allow it. **Decision rule needed**: gate must scope the path being written to the tree it belongs to (writes under `specs/releases/` consult release TASKS; writes under `specs/hotfix/` consult hotfix TASKS; writes under production paths consult both).

### Option γ — List/array of active items

```
active:
  - kind: release
    id: agent-sdd-alignment-v1
    phase: TASKS
  - kind: hotfix
    id: v1.2.1
    phase: HOTFIX_IMPLEMENTATION
```

Pros: most general.

Cons: YAML-ish format breaks the existing line-oriented `grep -E '^release:'` in `sdd-spec-gate.sh` L87. Forces gate to grow a YAML parser (and Python availability is fragile in the hook — the hook fails open, which would silently weaken every rule). Also breaks every existing skill that reads ACTIVE.md (search `cat .../ACTIVE.md`).

### Recommendation: Option β (dual pointer)

Strongly recommended, with the following constraints:

1. The two new keys (`hotfix:` and `hotfix_phase:`) are **optional**. If absent, behavior identical to today.
2. When present, both must be non-empty (extend `_read_active_md` to validate the pair).
3. `hotfix_phase` canonical values: a separate small set — `HOTFIX_DISCOVERY`, `HOTFIX_IMPLEMENTATION`, `HOTFIX_CLOSURE`, `HOTFIX_ARCHIVED`, `none`. Subset of release phases because hotfix data model is simpler.
4. Gate Rule A allows memory writes if `phase=CLOSURE` OR `hotfix_phase=HOTFIX_CLOSURE`.
5. Gate Rule C scopes the grep by target path: writes to a path under `specs/releases/` look at release TASKS; writes under `specs/hotfix/` look at hotfix TASKS; writes to production paths look at **both** and allow if either has `[-]`.

**Backward compat with the 10 legacy non-SemVer releases:** none of them have hotfixes; the hotfix keys are absent; gate and doctor behavior unchanged for them. See §10.

## 6. Gate v3 modifications needed

### 6.1 Rule A (memory atomicity)

Change at `sdd-spec-gate.sh` L96–104. Current literal pattern:

```bash
case "$FPATH" in
    */specs/memory/*.html|*/specs/memory/*.md|*/specs/memory/product/*.html|*/specs/memory/product/*.md)
        if [ "$ACTIVE_PHASE" != "CLOSURE" ]; then ... block ...
```

New:
```bash
case "$FPATH" in
    */specs/memory/...)
        if [ "$ACTIVE_PHASE" != "CLOSURE" ] && [ "$ACTIVE_HOTFIX_PHASE" != "HOTFIX_CLOSURE" ]; then ... block ...
```

Requires reading `hotfix:` and `hotfix_phase:` into shell vars at L86–89 alongside `release` and `phase`. Two more `grep`s and `sed`s. Trivial.

### 6.2 Rule B (archive read-only)

Extend pattern to cover `*/specs/_archive/hotfixes/*` (already covered by the existing `*/specs/_archive/*` wildcard — **no change needed**). Verify by reading L108–112.

### 6.3 Rule C (production write needs `[-]`)

Add a new candidate path before the existing release search (`sdd-spec-gate.sh` L159–175):

```bash
# Priority order updated:
# 0. NEW: PRIMARY_SPECS/hotfix/<active-hotfix>/TASKS.md (if hotfix in flight)
# 1. PRIMARY_SPECS/releases/<active-release>/TASKS.md
# 2. Any PRIMARY_SPECS/releases/*/TASKS.md
# 3. Any PRIMARY_SPECS/hotfix/*/TASKS.md
# 4. Legacy features/* (when SDD_LEGACY_FEATURES=1)
```

The hotfix grep is inserted at priority 0 — if a hotfix is the active emergency, its tasks take precedence. Then the existing release search; then a fallback that scans all hotfix dirs (someone may have multiple hotfix-tracked patches in flight, although the dual-pointer model in §5 forbids this).

### 6.4 New rule for hotfix-specific paths (HOTFIX.md as meta-edit)

The meta-edit allow-list at L114–121 currently lists `*/TASKS.md|*/PLAN.md|*/SPEC.md|*/CLOSURE.md|*/ACTIVE.md|*/z_bug_specs.md|*/backlog/*.md`. Add `*/HOTFIX.md` to the list, otherwise the very file the hotfix process needs to write is not authorized by meta-edit allow.

### 7.3 SemVer regex validator

```python
SEMVER_RE = re.compile(r"^v(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)$")
```

The spec for **release-id** under the new model: `^<project-slug>-v\d+\.\d+\.\d+$` (e.g. `dadaia-workspace-panel-v1.2.0`). The spec for **hotfix-id**: `^v\d+\.\d+\.\d+$` (e.g. `v1.2.1`). The hotfix-id does NOT include the project slug because it lives under `specs/hotfix/` (already scoped by tree); the release-id includes the slug because future cross-repo release-id collisions are real.

**Open question**: should the slug+version composite be enforced, or is the bare version enough? See §12.

### 7.4 Migration tolerance — the 10 legacy releases

The existing 10 releases (`dev-workspace-governance`, `multi-agent-orchestration`, …, `agent-sdd-alignment-v1`) are **none of them** SemVer-conformant. Two approaches:

| Strategy | Description | Cost |
|---|---|---|
| **Cutoff date** | Mirror `HARD_LIMIT_PLAN_CUTOFF` precedent (`doctor.py` L55): SemVer enforcement is WARNING for releases with `Created:` ≤ <date>, ERROR after. | Same pattern operator already accepted in `SPEC-DOC-005`. **Recommended.** |
| **Explicit allow-list** | Doctor reads a `legacy-releases.txt` of 10 names; everything outside the list must match SemVer. | Adds a sidecar config file; deviates from precedent. |
| **Leave legacy as-is** | SemVer enforced only for releases created from now on, by directory mtime or `Created:` field. | Cheapest but inconsistent — the file inside is the source of truth. |

**Recommendation:** cutoff date, paired with a doctor escape hatch for hotfix-id (which never has a `Created:` field on a directory level — `HOTFIX.md` has the date inside).

## 11. Risks

### 11.1 Hotfix track becoming a "spec-light backdoor"

The biggest architectural risk. `HOTFIX.md` is shorter than `SPEC.md` by design. If the team treats it as "the way to skip approval", every contentious change will be filed as a hotfix.

Mitigations:
- Gate requires `**Status:** Aprovado` on `HOTFIX.md` before allowing production writes (extend Rule C to also check status of the active spec, not just `[-]` task marker). Currently the gate only checks task marker, not status — adding status check is a real strengthening but requires `grep` on `**Status:**` line of the active spec.
- `qa-engineer` "Hotfix candidate" report is the only authorized entry point to HOTFIX_DISCOVERY. A hotfix opened without a qa-engineer report attached fails doctor's `SPEC-DOC-014` (`Patches release` field requires a regression source).
- PLAN.md absence is a feature, not a bug — but if hotfix grows beyond ~3 tasks, doctor emits WARNING "consider reclassifying as MINOR release".

### 11.2 ACTIVE.md complexity exploding

Dual pointer is the minimum complexity that works. Adding more (release-pipeline state, deploy-pending flag, etc.) would compound — explicitly out of scope. The schema must be **frozen** at 4 keys (`release`, `phase`, `hotfix`, `hotfix_phase`) by this SPEC.

### 11.3 Memory atomicity violations if hotfix writes memory outside CLOSURE

The gate already enforces phase-gated memory writes (Rule A). The dual-pointer extension preserves this — memory unlocks ONLY in `phase=CLOSURE` (release) OR `hotfix_phase=HOTFIX_CLOSURE`. **Critical implementation note**: when both pointers are active and BOTH happen to be in CLOSURE simultaneously, the gate cannot distinguish whose CLOSURE is unlocking memory. This is a real failure mode if two writes race — though in practice the operator serializes CLOSURE phases (they require human approval anyway).

### 11.4 Doctor false negatives during migration

If the SemVer regex is enforced as ERROR before the cutoff, every existing archived release fails doctor immediately. Use the WARNING-then-ERROR pattern from `SPEC-DOC-005`.

### 11.5 `bug-fix-fastlane` workflow drift

The existing workflow today bypasses `specs/`. With hotfix track in place, fastlane should optionally feed into HOTFIX_DISCOVERY — but mandating it would break the "no-spec for trivial fixes" property the workflow gives. **Recommendation**: leave `bug-fix-fastlane.workflow.md` as the entry point for tiny bugs; introduce a new workflow `hotfix-track.workflow.md` for incidents that demand a HOTFIX.md trail. Two workflows, two severities — preserves the existing tool.

## 12. Open questions for product-engineer / operator

These are decisions only the operator can settle — anchored in code, blocking on the spec:

1. **Hotfix-id format**: SemVer-only (`v1.2.1`) or slug+SemVer (`dadaia-workspace-panel-v1.2.1`)? The slug-prefixed form makes cross-workspace lookups unambiguous but adds verbosity. Anchored: `specs/_archive/legacy-features/release-pipeline/SPEC.md` FR-REL-024 (L138) uses `v` + SemVer alone.
2. **Project-versioned releases**: does the SemVer apply to the product as a whole (`dadaia-workspace-v0.5.0`) or per-release-id with its own version (`agent-sdd-alignment-v0.1.0`)? Today release-ids are descriptive slugs ending in `-v1`. SemVer per "release line" (e.g. `panel-v1.x.y`) vs SemVer per product (`dadaia-workspace-vX.Y.Z`) are very different mental models — pick one.
3. **Single ACTIVE.md vs split**: §5 recommends dual pointer in one file. Alternative is two files: `specs/releases/ACTIVE.md` and `specs/hotfix/ACTIVE.md`. The gate already reads ACTIVE.md once; reading two files doubles I/O. But two files are atomic to write independently. Cost/benefit tilts toward dual pointer in one file, but operator's preference matters.
4. **Hotfix CLOSURE updates memory or not by default?** A hotfix that fixes a typo doesn't touch product memory. A hotfix that uncovers an undocumented behavior must. Default: memory updates **optional** for hotfix CLOSURE (analogous to release CLOSURE's `## Memory updates` which can be "none"). Confirm.
5. **Status ladder for HOTFIX.md**: `Draft → Em revisão → Aprovado` is the canonical ladder. For a 2-hour incident response, requiring three status flips is friction. Alternative: hotfix-only status `Open → Patched → Closed`. Decide whether to extend `CANONICAL_STATUS` (`doctor.py` L34) or reuse.
6. **Can a hotfix span repos?** Today releases are per-context-project. A hotfix on `dadaia-workspace` that requires a coordinated patch to `redacted-slug` is an open architectural question. Recommend: **no** — each repo files its own hotfix. Cross-repo orchestration via `dadaia orchestrate run`.
7. **What triggers HOTFIX_ARCHIVED?** Release archiving today is gated by CLOSURE completion + `git mv` (`product-engineer.md` L345–353). For hotfix, the equivalent is the deployed binary plus a CI tag. Who decides? Likely devops-engineer's domain — the **decision criterion** (commit on `main` matches `git tag v1.2.1`?) is operator's call.
8. **Doctor errors vs warnings for `SPEC-DOC-013..017`**: ERROR is strict; WARNING is permissive during migration. Recommend ERROR from day one for new hotfixes (small new feature, no installed base) but WARNING for legacy mismatches found during scanning.
9. **Should hotfix write to memory in the same way release CLOSURE does (via `dadaia public install` cycle of templates)?** Or is there a lighter path? Memory templates already exist in `public/templates/memory-*.html.j2`. Recommend: reuse same path — no parallel pipeline.
10. **Inconsistency flag for the operator**: the candidate description in `specs/backlog/candidates.md` L22 says `vMAJOR.MINOR.PATCH for releases, with PATCH reserved for hotfixes`. This phrasing suggests **the same versioning space** for both releases and hotfixes (release bumps MAJOR/MINOR; hotfix bumps PATCH). My recommended model in §7.3 keeps them in the same space (release-id matches `<slug>-v\d+\.\d+\.\d+`, hotfix-id matches `v\d+\.\d+\.\d+` and references the patched release). Confirm: is this the operator's intent or did they mean two version axes?
