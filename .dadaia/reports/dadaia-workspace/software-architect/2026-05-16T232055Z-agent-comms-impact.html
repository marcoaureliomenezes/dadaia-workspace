1. Localização do schema

Decisão: dadaia_workspace/public/schemas/handoff-v1.schema.json (favorecido pelo briefing) é a localização correta e única. Não há alternativa que mantenha o invariante "public é a única fonte de authoring" (constitution L106: Neste repositório, dadaia_workspace/public/ é a única localização versionada para rules, skills, commands, scripts, agents e templates universais do produto).

Justificativa e projeção:

  • O Discovery FR1 já fixa o caminho. A alternativa que cogitei — colocar o schema sob dadaia_workspace/data/handoff-v1.schema.json, ou seja, como dado embutido no pacote em vez de asset versionável — quebra o contrato citado. Reports HTML existentes (ex. .dadaia/reports/dadaia-workspace/software-architect/2026-05-15-orchestration-audit.md) são produzidos no workspace runtime, fora do source tree do pacote; portanto o schema precisa ser projetado para o workspace, não embutido em data/ (que serve repos.xlsx e AGENTS.md — assets lidos pelo runtime mas não publicáveis para consumo de agentes externos).
  • Cadeia de projeção concreta: O canonical em public/schemas/handoff-v1.schema.json entra na cadeia regular via FileSystemPublicAssetManager.stage() (ver dadaia_workspace/infrastructure/public_assets.py:25-36, tupla _COPY_DIRS). Estágio produz .dadaia/agentic/schemas/handoff-v1.schema.json com sha256 no manifest.json (ver .dadaia/agentic/manifest.json — hoje contém entries para agents/, commands/, rules/, scripts/, templates/, workflows/, data/, plugins/). A linha 35 já lista "workflows" em _COPY_DIRS; adicionar "schemas" é a única mudança em public_assets.py para fechar FR1 staging.
  • Projeção em runtime trees (.claude/schemas/, .codex/schemas/, .opencode/schemas/): NÃO. Os tuples _CLAUDE_DIRS (public_assets.py:37) e _OPENCODE_DIRS (public_assets.py:38) listam apenas artefatos que o runtime de agente executa (rules, skills, commands, agents, workflows, plugins). O schema é consumido pela CLI (FR2 valida; FR3 skill referencia path do staging) — não pelo runtime do agente que dispara o LLM. Manter o schema apenas em .dadaia/agentic/schemas/ evita duplicação (4× mesmo arquivo em disco) e mantém uma única fonte de leitura. Esta decisão fecha DN10 do Discovery ( O handoff-v1.schema.json deve ser projetado para todos os runtimes [...] ou apenas para .dadaia/agentic/schemas/?): staging-only.
  • Implicação no doctor: dadaia_workspace/features/specs/doctor.py hoje valida workflows via _validate_workflows (linha 130) e classifica artefatos em _classify_workflows (linha 239). O public doctor separado (em cli/commands/public.py + public_assets.py) precisa reconhecer o novo tipo. NFR7 do Discovery declara que rodar dadaia public install --target all --force duas vezes e confirmar diff zero é o critério. Validação adicional do schema em si (i.e., schema válido segundo Draft 2020-12) é responsabilidade da CLI reports validate (FR2), não do doctor — separar concerns.

2. Módulo de feature: extender orchestration/ vs novo pacote handoff/

Decisão: criar novo pacote dadaia_workspace/features/reports_validation/ (NÃO handoff/, NÃO sub-módulo de orchestration/).

Justificativa por acoplamento de código:

  • O Discovery FR2 propôs literalmente dadaia_workspace/features/reports_validation/service.py. Mantenho a proposta porque ela é arquiteturalmente sólida quando comparada às alternativas:
  • Por que não estender orchestration/: O escopo de orchestration/ é, segundo 2026-05-15-orchestration-audit.md §1.2 e FR-ORCH-024 da SPEC dessa feature, exatamente três módulos: service.py, runner.py, resolver.py. Adicionar handoff.py ali violaria essa restrição declarada na própria SPEC da feature. Mais grave: o consumidor primário do handoff validation não é o orchestration service. É a CLI standalone dadaia reports validate [path|--all] (FR2 do Discovery) e futuramente — em v2, fora deste escopo — o _resolve_awaiting_gates do orchestration service. Acoplar já agora a feature de validação à de orquestração é premature abstraction (ver architect-design-patterns skill) com risco direto de criar ciclo lógico: orchestration depende de validation que depende de modelos de workflow que vivem em core/models/workflow.py — esse caminho fica limpo apenas se reports_validation viver em pacote irmão.
  • Por que não features/handoff/: "handoff" é o nome do artefato (o sidecar *.handoff.json), não da capacidade. A capacidade é "validar reports contra um contrato declarado". O nomeamento reports_validation reflete a responsabilidade exata da feature (verb + object) e alinha com a CLI (dadaia reports validate). Em v2/v3 a mesma feature pode ganhar reports_validation.contract_check para orchestration must_include — o nome continua certo. "handoff" é domínio de schema, não de feature.
  • Forma concreta: 
    dadaia_workspace/
├── core/
│   ├── models/handoff.py          # dataclass HandoffDocument (DTO de leitura)
│   ├── protocols/handoff_validator.py  # Protocol ValidatorPort
│   └── exceptions.py              # +HandoffSchemaError, +HandoffValidationError
├── features/
│   └── reports_validation/
│       ├── __init__.py
│       └── service.py             # ReportsValidationService
└── infrastructure/
    └── stdlib_handoff_validator.py  # adapter (ver decisão #4)
    Esta forma:
    • Mantém regra de camadas estrita: feature depende só de core/protocols/handoff_validator.py; adapter implementa o Protocol.
    • Permite que OrchestrationService._resolve_awaiting_gates em v2 receba o mesmo ValidatorPort via composition root, sem criar import direto entre features/orchestration e features/reports_validation (que a constitution L67 proíbe: Nenhuma feature importa outra feature.).

3. CLI namespace: dadaia reports validate (novo Typer app) vs sub-comando de orchestrate

Decisão: novo Typer app dadaia_workspace/cli/commands/reports.py montado em cli/main.py como app.add_typer(reports.app, name="reports"). Não submontar sob orchestrate.

Justificativa:

  • Escopo de comando ≠ escopo de feature. O verbo orchestrate hoje significa "iniciar/monitorar/resumir runs" (subcomandos atuais: list, show, run, status, resume — ver dadaia_workspace/cli/commands/orchestrate.py:71-300). Anexar orchestrate reports validate mistura dois domínios conceituais: run de workflow (estado) e validação de contratos (assertiva). Inspeção do top-level CLI (cli/main.py:31-38) mostra que os apps top-level seguem o padrão noun: context, repos, public, doctor, academy, orchestrate (verb, porém único), specs, server. Adicionar reports mantém esse padrão e abre espaço para v2/v3 expandir (dadaia reports next, dadaia reports list, dadaia reports emit) sem refactor.
  • Cobertura de operador casual. Operador procurando "validar meu handoff" digita dadaia reports --help antes de dadaia orchestrate --help. Affordance correta minimiza descoberta-tempo.
  • Reuso em CI (v2). NFR4 do Discovery declara que esta release não adiciona gate em CI; v2 sim. O job em .github/workflows/ci.yml rodará dadaia reports validate --all --strict de qualquer árvore — não faz sentido CI invocar dadaia orchestrate reports validate (verbo confuso, sugere orquestração) versus dadaia reports validate (substantivo + verbo limpo).
  • Forma concreta da CLI v1: 
    dadaia reports validate <path-or-dir>     # arg posicional
dadaia reports validate --all              # itera .dadaia/reports/<context>/**/*.handoff.json
dadaia reports validate <path> --strict    # exit 2 em qualquer falha
dadaia reports validate <path> --json      # output estruturado em stdout
    Default --strict=false conforme NFR2. Exit codes idênticos ao padrão do CLI existente (orchestrate.py retorna typer.Exit(2) em erro semântico; typer.Exit(1) em workspace não inicializado).

4. Validador: stdlib-only (regex+manual para subset Draft 2020-12) vs jsonschema

Decisão recomendada: stdlib-only validator em v1 (dadaia_workspace/infrastructure/stdlib_handoff_validator.py). Adicionar jsonschema como dependência é desnecessário neste escopo e custa atualização formal da constitution (specs/constitution.md L17–28, com decisão de operador per L451 do product-engineer.md).

Análise dos trade-offs:

Critério stdlib-only jsonschema PyPI
Constitution impact Zero — não toca tabela L17–28 Requer update formal de L17–28 + grill-me confirmation (per product-engineer.md L451)
LoC do adapter ~80 LoC (NFR3 do Discovery) ~25 LoC (Draft202012Validator wrap)
Cobertura do schema (FR1 — campos schema_version, agent, context, release_id, produced_at, artifact.{type,path,content_hash}, findings[], decisions_required[], next_handoff) Suficiente: type, required, enum, pattern (regex via stdlib re), additionalProperties, validação de ISO 8601 via datetime.fromisoformat. Esses são os únicos keywords necessários para FR1. Plena: meta-schema 2020-12, $ref, allOf, oneOf, etc. — mas nenhum desses é demandado por FR1.
Mensagens de erro Controle total — pode cumprir constitution L137 (informar a capacidade ou comando que falhou, o contexto ou recurso relevante e a próxima ação segura de recuperação) Mensagens do jsonschema exigem wrapping para cumprir L137; ganho de simplicidade é parcialmente neutralizado

5. Skill dadaia-handoff-emitter: standalone SKILL.md vs subcomando dadaia reports emit

Decisão: standalone skill em dadaia_workspace/public/skills/dadaia-handoff-emitter/SKILL.md (favorecido pelo briefing). Não criar dadaia reports emit em v1.

Justificativa:

  • Quem emite o handoff é o LLM, não a CLI. O conteúdo do sidecar (findings[], decisions_required[], next_handoff.target_agent) deriva do trabalho semântico que o agente acabou de fazer. Uma CLI dadaia reports emit teria que receber todo esse payload como flags (--finding 'CRITICAL: ...'), o que é UX impossível para arrays longos, ou ler stdin JSON — caso em que a CLI vira um jq de luxo sem valor adicional. A skill instrui o LLM a montar o JSON e escrevê-lo via Write tool, que é a forma natural na 27-skills convention já presente em dadaia_workspace/public/skills/ (ver dadaia-grill-me, dadaia-release-closure, dadaia-task-manager como precedentes).
  • Verificação assimétrica é robusta. Emissão é livre (qualquer agente pode escrever um *.handoff.json com qualquer conteúdo); validação é estrita (dadaia reports validate bloqueia o que não bate). Esta separação emit free / validate strict é mais defensiva que emit gated / validate strict: se a skill estiver bugada em algum agente, o operador descobre via validate, não via crash do emit.
  • Composição com outras skills. Os pilotos (product-engineer, software-architect, software-engineer) já carregam 3–4 skills (ver frontmatter de public/agents/product-engineer.md:21-26: dadaia-workspace-spec-navigator, dadaia-grill-me, dadaia-task-manager, dadaia-release-closure). dadaia-handoff-emitter entra como peer dessas — invocação ao final, padrão consistente. Subcomando CLI quebra esse padrão sem ganho.
  • Forma concreta da skill (SE detalha em Phase 3): protocolo de 3 passos no SKILL.md — (a) computar content_hash via Bash sha256sum <report.html>; (b) montar o JSON com campos obrigatórios + opcionais derivados do report; (c) escrever <mesmo-stem>.handoff.json ao lado do HTML usando Write. Skill projetada via cadeia normal (public/skills/ → .dadaia/agentic/skills/ → projeções .claude/skills/, .codex/skills/ via .agents/, .opencode/skills/).

Trade-off explícito: uma skill é menos testável que um subcomando CLI (não há CliRunner equivalente para skills). Compensa porque o gate real é validate, não emit; e porque a skill é instrução textual versionada — drift é detectável via dadaia public doctor.

Decisions

Lista numerada das decisões arquiteturais que assumo nesta release. Cada item: escolha + racional + trade-off. As decisões propriamente operacionais (que envolvem implementação) ficam para o SE em Phase 3 — aqui registro só o que define onde as coisas vivem e como dependem uma da outra.

A1 — Schema canonical em public/schemas/handoff-v1.schema.json, projetado apenas a staging.

Escolha: aceitar a localização favorecida do briefing; não projetar para runtime trees (.claude/schemas/ etc.).

Racional: schema é consumido pela CLI (FR2) e pela skill (FR3), que leem do staging via .dadaia/agentic/schemas/. Runtimes do LLM não precisam do JSON em disco — a skill dadaia-handoff-emitter tem o contrato em prosa.

Trade-off: agentes externos que quisessem validar o schema fora da CLI oficial precisarão ler de .dadaia/agentic/schemas/ em vez de seu próprio runtime tree. Custo: 0 — não é caso de uso pleiteado.

A2 — Feature em pacote irmão features/reports_validation/ (não em orchestration/).

Escolha: novo pacote em dadaia_workspace/features/reports_validation/ com Protocol em core/protocols/handoff_validator.py e adapter em infrastructure/stdlib_handoff_validator.py.

Racional: cumprir constitution L67 (Nenhuma feature importa outra feature.); cumprir FR-ORCH-024 da SPEC de orchestration (exatamente três módulos: service.py, runner.py, resolver.py); evitar premature abstraction de acoplar validation à orquestração antes de v2.

Trade-off: dois pacotes de feature em vez de um. Custo marginal — fica claro em dadaia_workspace --help e em onboarding.

A3 — CLI namespace top-level dadaia reports, novo Typer app.

Escolha: cli/commands/reports.py com app = typer.Typer(...); cli/main.py recebe app.add_typer(reports.app, name="reports") na linha pós-orchestrate (após L36).

Racional: alinhamento com convenção noun-based dos demais top-level apps (context, repos, public, specs); abre espaço para v2/v3 sem refactor; CI v2 invoca verbo limpo.

Trade-off: 1 namespace a mais no --help root. Custo marginal; ganho de discoverability é maior.

A4 — Validador stdlib-only em v1 (sem dep jsonschema).

Escolha: StdlibHandoffValidator em dadaia_workspace/infrastructure/stdlib_handoff_validator.py implementando ValidatorPort; suporta keywords type, required, enum, pattern, properties, items, additionalProperties, format=date-time.

Racional: cumprir NFR3 do Discovery (Zero novas dependências de runtime obrigatórias); evitar gatilho de atualização formal da constitution; manter controle total sobre mensagens de erro (constitution L137).

Trade-off: ~55 LoC a mais que adapter jsonschema; e não suporta composição de schemas ($ref, allOf). Quando v2/v3 demandarem composição, retomar decisão.

A5 — Skill standalone dadaia-handoff-emitter (não subcomando CLI).

Escolha: dadaia_workspace/public/skills/dadaia-handoff-emitter/SKILL.md com protocolo de 3 passos: content_hash via sha256, montagem do JSON, escrita do sidecar.

Racional: emissão é trabalho semântico do LLM; CLI seria proxy sem valor. Padrão de skills (27 hoje em public/skills/) é precedente.

Trade-off: menos testável que CLI; drift detectado por dadaia public doctor apenas. Aceitável porque o gate real é o validate.

A6 — Adicionar "schemas" à tupla _COPY_DIRS em public_assets.py:25-36.

Escolha: mudança pontual de 1 linha em dadaia_workspace/infrastructure/public_assets.py:35 (inserir "schemas", antes de "workflows" ou ao final). Não adicionar a _CLAUDE_DIRS, _OPENCODE_DIRS (consistente com A1).

Racional: NFR7 do Discovery (FileSystemPublicAssetManager reconheça o novo tipo schemas); SE implementa em Phase 5 como parte de FR1.

Trade-off: requer que o doctor classifique schemas/ — verificar em features/specs/doctor.py ou no fluxo public-doctor que itera o staging dir. Esforço S; sem trade-off arquitetural.

A7 — Modelo HandoffDocument dataclass em core/models/handoff.py (DTO).

Escolha: dataclass frozen=True espelhando a estrutura do schema (campos: schema_version: str, agent: str, context: str, release_id: str | None, produced_at: str, artifact: ArtifactRef, findings: tuple[Finding, ...], decisions_required: tuple[str, ...], next_handoff: NextHandoff | None).

Racional: alinha com padrão de core/models/workflow.py e core/models/run_state.py (ver auditoria 2026-05-15 §1.2: dataclasses frozen são a convenção). Pure domain — sem I/O — testável em isolamento. Permite que v2 e além troquem o adapter de validação sem mover o modelo.

Trade-off: 1 arquivo a mais em core/models/. Custo zero; e abre porta para HandoffDocument.from_json(text: str) como parser puro no domínio.

A8 — Protocol ValidatorPort em core/protocols/handoff_validator.py.

Escolha: typing.Protocol com método validate(doc: dict) -> Sequence[HandoffValidationError]; vazio = válido. Exceções de domínio em core/exceptions.py: HandoffSchemaError (schema arquivo inválido) e HandoffValidationError (instance não satisfaz schema).

Racional: cumprir constitution L69 (Toda dependência externa usada por features/ deve passar por um Protocol definido em core/.). Permite que orchestration em v2 receba o mesmo ValidatorPort via container sem importar features/reports_validation.

Trade-off: 1 Protocol + 2 exceptions adicionais em core/. Custo zero; ganho de testabilidade alto (fake validator trivial em testes).

A9 — Composition wiring em dadaia_workspace/container.py.

Escolha: nova função build_reports_validation_service(workspace_root: Path) -> ReportsValidationService no container, paralela a build_orchestration_service. Lê o schema de workspace_root / ".dadaia" / "agentic" / "schemas" / "handoff-v1.schema.json"; instancia StdlibHandoffValidator(schema_path); passa ao service.

Racional: cumprir constitution L63 (container.py é a composition root). Mantém regra: CLI nunca instancia StdlibHandoffValidator diretamente.

Trade-off: container.py cresce. Esperado e correto. A auditoria 2026-05-15 LOW finding "_select_dispatcher faz import os dentro da função" recomenda imports no topo — manter esse padrão em A9.

A10 — Skill content schema-aligned (não duplicado).

Escolha: a skill SKILL.md referencia o schema por path lógico (.dadaia/agentic/schemas/handoff-v1.schema.json) e descreve em prosa apenas os campos obrigatórios. Não duplica o schema em JSON dentro do markdown — o schema é fonte única de verdade.

Racional: evita drift entre prosa-da-skill e schema-canonical; cumpre o princípio "single source of truth".

Trade-off: agente precisa ler dois arquivos (SKILL.md + schema) ao executar a skill. Custo de tokens: ~2 KB extras por invocação — irrelevante.

A11 — Migração z_bug_specs.md NÃO é parte da feature reports_validation.

Escolha: a migração descrita no Discovery §4 é orquestrada por specs/releases/agent-comms-v1/TASKS.md (a ser produzido em Phase 5 pelo PE) como tasks isoladas T-MIGRATE-Z-BUG-001 e T-MIGRATE-Z-BUG-002 (per DN5). Não toca código de features/reports_validation/ ou features/orchestration/.

Racional: a migração é puramente operação documental + 3 consumers patches + 1 entry no sdd-spec-gate.sh:117. Acoplá-la à feature técnica introduziria coupling falso ("a feature de validação deletou meu z_bug_specs?").

Trade-off: zero. Estritamente desentrelaça concerns.

A12 — Pilotos em D1 são exatamente os 3 do Discovery DN6: product-engineer, software-architect, software-engineer.

Escolha: aceitar a recomendação do PE (Discovery §6) sem alteração. Inspeção do spec-refinement.workflow.md confirma: linhas 17 (discovery → product-engineer), 33 (arch_review → software-architect), 88 (synthesis → product-engineer). O SE entra via tdd-cycle.workflow.md. Os 3 cobrem os agentes invocados em todos os workflows seed.

Racional: validação em produção (workflows reais) em vez de exercício hipotético. Discovery §6 já argumentou; verifico e refrendo.

Trade-off: qa-engineer não emite handoff em v1 — risco R4 do Discovery, aceito por NFR2 (strict=false).
