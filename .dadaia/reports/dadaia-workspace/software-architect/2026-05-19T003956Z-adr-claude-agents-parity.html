ADR — Byte-Identical CLAUDE.md / AGENTS.md Across Projection Targets

Context

Release agents-r2-v1 (SPEC §FR7) mandates that the lib ship two filenames — CLAUDE.md and AGENTS.md — with byte-identical content, projected by dadaia public install to four projection roots: workspace root (<workspace>/CLAUDE.md + AGENTS.md) and consumer-repo roots (repos/<slug>/CLAUDE.md + AGENTS.md). Different harnesses read different conventions (Claude Code reads CLAUDE.md; Codex and OpenCode read AGENTS.md) but the guardrails are the same. PE flagged FR7.0 as an open architect question with three candidate mechanisms (symlink at source, doctor-enforced parity check, generate-from-single-source-at-install). This ADR settles the mechanism. The current installer (dadaia_workspace/infrastructure/public_assets.py) is 100% shutil.copy2() plus atomic writes — zero symlink emission, SHA256-based doctor comparisons — and projects AGENTS.md to only the workspace root, so any mechanism chosen will require extending the installer to a 4-target loop regardless.

Options weighed

Option Mechanism Pros Cons Risk profile
A — Symlink in source tree Source: one regular file (data/AGENTS.md) + one symlink (data/CLAUDE.md → AGENTS.md). Installer reads source via the symlink and materialises two regular files at each target. Single editable source guaranteed at the lib layer. Reading either name returns identical bytes through the same inode. Three structural problems against the existing code: (1) the staging step uses shutil.copytree(src, dst) at data/ (line 313), and the default symlinks=False dereferences the symlink at stage time — so the symlink is silently lost in .dadaia/agentic/data/ and the source-of-truth nature is broken before install runs. (2) Manifest construction iterates files and computes SHA256 per path (_build_manifest, line 452) — a dereferenced symlink would record two identical hashes but the second file would not actually exist on disk in the source, which the existing dadaia public doctor source-walk would flag. (3) Git tracks symlinks as mode 120000 with the target path as content — diff readability degrades, and any contributor on macOS APFS-case-sensitive or in an editor that opens the symlink rather than the target risks editing the wrong file. High structural risk. Forces a special case in stage() (symlinks=True) AND a special case in _iter_files AND a special case in _build_manifest. Three places to break.
B — Doctor-enforced parity Source: two independent regular files (data/CLAUDE.md + data/AGENTS.md) authored side by side. doctor grows a new invariant: SHA256 equality across the two source files and across every pair of sibling projections. Drift fails the doctor run. Plain files everywhere; no special semantics. Doctor already does SHA256 comparisons — adding a sibling-pair invariant is a 5-line extension. Two real problems: (1) drift can exist transiently in the source tree if a developer edits one file and forgets the other — there is no commit-time gate, only a doctor-time gate. (2) Two parallel sources means two chances to make a content mistake; the burden of "keep them identical" sits with the lib maintainer, not the tool. Doctor is opt-in (CI may not run it; nothing forces it before install). Medium risk. Catches drift after the fact, not before. Two editable sources in the source tree means a non-zero rate of "I forgot the other file" mistakes.
C — Single source, generated at stage/install Source: ONE regular file at data/AGENTS.md. data/CLAUDE.md does NOT exist in the source tree. The installer writes BOTH names at each projection root from the single source. Doctor compares both projections to the same source SHA256. Single source of truth — physically impossible to have drift between the two lib sources because there is only one lib source. Install guarantees parity as a consequence of using one input. Manifest entry stays clean: one path (data/AGENTS.md) with one hash, but the doctor's _runtime_expectations emits four projection lines (root:CLAUDE.md, root:AGENTS.md, repo:CLAUDE.md, repo:AGENTS.md) all pointing to the same source. Fits the existing _compare(src, dst, label) pattern with no special case. Install is non-idempotent for manual edits to either projected file — they get overwritten on next install --force. This is the correct behaviour (per the existing dadaia-workspace-dev-guardrail rule that already forbids editing lib-originated projections), but surprising to anyone who does not understand the projection model. Mitigated because the guardrail rule already exists and applies — workspace-root CLAUDE.md becomes a lib projection in this release, which is exactly the contract the guardrail rule covers. Low risk. Zero new code paths beyond a 4-target loop. Zero new special cases in the manifest or doctor logic. The only change in operator semantics is one already codified by an existing rule.

Decision

Adopt Option C — single source data/AGENTS.md, generated to both filenames at install time, at four projection roots.

Rationale: this is the only option where parity is a structural property rather than a process property. With one source file, drift between CLAUDE.md and AGENTS.md is not just unlikely — it is impossible to express. The lib maintainer cannot accidentally edit one and not the other because there is nothing to edit twice. Option A introduces three special cases in copytree, _iter_files, and _build_manifest to preserve a symlink the rest of the code is not designed to see; Option B leaves the parity contract enforced by a process the developer must remember to run. Option C maps cleanly onto the existing _compare(src, dst, label) infrastructure — one source, many projection destinations.

Consequences

Changes in lib source tree

  • dadaia_workspace/public/data/AGENTS.md — rewritten per FR7.1–FR7.9 (already a SPEC obligation, independent of this ADR).
  • dadaia_workspace/public/data/CLAUDE.md — does NOT exist. The lib has one editable source for both filenames.

Changes in infrastructure/public_assets.py

  • _install_agents_md() (line 467) is renamed _install_workspace_guardrail_pair() and rewritten to project the single source data/AGENTS.md to FOUR destinations:
    • workspace_root / "AGENTS.md"
    • workspace_root / "CLAUDE.md"
    • workspace_root / "repos" / <consumer_slug> / "AGENTS.md" — only if the consumer-repo directory already exists (idempotent skip otherwise)
    • workspace_root / "repos" / <consumer_slug> / "CLAUDE.md" — same guard
  • _runtime_expectations() (line 583) yields four tuples for these projections instead of one — each pointing back to the same data/AGENTS.md source with a distinct label (root:AGENTS.md, root:CLAUDE.md, repo:AGENTS.md, repo:CLAUDE.md).
  • The "consumer slug" is the same value already used in _opencode_config (line 775) to assemble repo-scoped instructions — reuse, do not invent a new discovery mechanism.
  • The _agents_md_source() lookup priority (templates/AGENTS.md then data/AGENTS.md) stays as-is.

Changes in doctor

  • No new pairwise sibling check is required — each of the four projections is compared against the single source via the existing _compare() path. Byte equality across siblings is a consequence, not a separately enforced invariant.
  • FR7.10 also mentions "an explicit sha256sum parity check comparing CLAUDE.md vs AGENTS.md at every projection root". Under Option C this check is logically redundant (both files are _compare()'d against the same source) but PLAN should still emit a parity report line per projection root for operator visibility — labelled [ok] parity:<root> (CLAUDE.md ≡ AGENTS.md) — so that operators reading the doctor output see the invariant they care about explicitly stated, not inferred.

Changes in .dadaia/agentic/manifest.json

  • The manifest tracks one source asset: data/AGENTS.md, with one SHA256.
  • It does NOT gain a data/CLAUDE.md entry — there is no such source file. The projections at each root are recorded by doctor output, not by the source-manifest.
  • This contradicts the literal wording of FR7.11 (which assumes the lib tracks two source paths). PLAN must reconcile: under Option C, FR7.11 becomes "manifest tracks the single source data/AGENTS.md; doctor emits four projection labels deriving from it". PE should accept this edit when writing PLAN.

Changes in operator workflow

  • To edit the lib pair: edit dadaia_workspace/public/data/AGENTS.md, run dadaia public stage && dadaia public install --target all. Both CLAUDE.md and AGENTS.md at all four roots are rewritten from the single source.
  • Operators must NOT hand-edit projected CLAUDE.md or AGENTS.md at any root. The existing dadaia-workspace-dev-guardrail rule already prohibits this for lib-originated projections; FR6.4 absorbs that rule's body into the lib pair itself, so the prohibition becomes self-documenting.
  • If the operator wants domain-scoped guardrails for services/ (FR10), they author services/CLAUDE.md + services/AGENTS.md as a separate, operator-managed pair. The lib installer does not touch nested paths — the four-target loop only writes to workspace-root and repo-roots — so nested files are never hash-locked. This is verified by the file scope: _install_workspace_guardrail_pair writes to enumerated destinations only, never recurses into subdirectories.

How to undo

  • If Option C proves wrong (e.g. operator needs the two files to genuinely diverge on some axis), reverting is one PR: split the single source into two regular files and remove the "two destinations per root" loop. Manifest reverts to tracking both sources. No data loss — every projection is reproducible from the source tree at any point.

Migration plan

There is no prior mechanism to migrate from — today the installer projects only AGENTS.md to workspace_root, and the workspace-root CLAUDE.md is a hand-authored, non-lib-projected operator file (FR10 explicitly calls this out: workspace-root CLAUDE.md content moves to services/CLAUDE.md + services/AGENTS.md as an operator-managed domain-scoped pair). The migration is therefore a one-shot per FR10 — operator manually copies the current product-content into services/{CLAUDE,AGENTS}.md BEFORE or AT the same install that activates the FR7 pair — after which install overwrites workspace-root CLAUDE.md with the new lib content. No legacy mechanism to retire; no symlinks to clean up; no half-states to recover from. The manifest's existing single-entry pattern for data/AGENTS.md stays; only the projection fan-out changes.

Open items handed to PE for PLAN

  1. FR7.11 wording fix. Under Option C, the manifest tracks only data/AGENTS.md (one source asset). FR7.11 currently reads as if the manifest gains a data/CLAUDE.md entry. PE must reword FR7.11 to: "manifest continues to track the single source data/AGENTS.md; the installer projects this source to four destinations (workspace_root/AGENTS.md, workspace_root/CLAUDE.md, repos/<slug>/AGENTS.md, repos/<slug>/CLAUDE.md); doctor emits one [ok] line per projection deriving from the same source SHA256."
  2. Consumer-repo slug discovery contract. PLAN must specify the rule for which repos/<slug>/ directories receive the projection. Three candidates:
    • (a) Every directory under repos/ that contains a .dadaia/ marker (signals: this is a dadaia-aware consumer).
    • (b) Every directory under repos/ that already contains an AGENTS.md (signals: previously projected).
    • (c) An explicit list under .dadaia/agentic/manifest.json (or workspace config).
    Architect recommendation: (a) — the .dadaia/ directory is the canonical consumer-marker already used by the rest of the workspace, and it avoids the chicken-and-egg of "first install needs an existing AGENTS.md". PE should nail this down in PLAN before TASKS is written, because _install_workspace_guardrail_pair needs a deterministic discovery routine.
  3. New install-CLI flag (optional, defer to operator). Consider a --repos-only / --workspace-only filter so an operator doing a hotfix to a single consumer-repo's projections does not have to re-stage everything. NOT a blocker for v1 — flag it as a P3 backlog item, not a release-r2 obligation.
  4. Doctor output label scheme. Four new labels are emitted: confirm the operator-readable convention. Recommendation: root:AGENTS.md, root:CLAUDE.md, repo:<slug>:AGENTS.md, repo:<slug>:CLAUDE.md. Plus the redundant-but-explicit parity line: parity:root, parity:repo:<slug>.
  5. Idempotent skip behaviour for absent consumer-repos. If repos/dadaia-workspace/ does not exist at install time (e.g. fresh clone of a different shape), _install_workspace_guardrail_pair must log [skip] repo:<slug>:AGENTS.md (target dir absent) rather than fail or auto-create. Existing _copy_file creates parent dirs on demand, so PLAN must specify the existence-guard explicitly to override that default for the repo-root case.
  6. FR7.10 verification — explicit parity line. Even though parity is structural under Option C, PLAN should still produce the operator-visible parity line per root (see "Changes in doctor"). PE: include this as a TASKS-level deliverable when authoring PLAN.
  7. Nested pair safety test. PLAN should include a TASKS-level deliverable: a test asserting that services/CLAUDE.md + services/AGENTS.md can diverge from the lib pair WITHOUT triggering doctor failure. This verifies the architectural intent that nested pairs are out of scope for the lib installer.
