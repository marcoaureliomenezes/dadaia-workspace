Spec-context cross-session isolation — RCA

Date: 2026-05-17T06:49:15Z Context: dadaia-workspace Author: software-engineer Severity: MEDIUM

Symptom

When two Claude Code sessions run concurrently against the same dadaia workspace, a dadaia context activate <name> call in Session A overwrites primary_context.json, and Session B immediately observes the change on the next UserPromptSubmit hook execution — even though Session B never requested a context switch. Both sessions read the same global state file; there is no per-session isolation.

Concrete scenario observed by the operator: Session A switches to context agent-monitoring-v1. Session B, which was working in dadaia-workspace, now sees [agent-monitoring-v1] injected into every prompt and the SDD gate allows writes to the wrong repo.

Resolution order

All readers follow the same priority chain (confirmed in ctx-inject.sh lines 11–31):

  1. DADAIA_CONTEXT env var — if set and a matching repos/<name>/specs/ directory exists, this wins unconditionally and primary_context.json is not read.
  2. primary_context.json global file — parsed with python3 -c "import json; ..."; name field extracted.
  3. Fallback — if neither resolves, the hook prints [context: none] and suggests the operator run eval $(dadaia context use <name>).
Isolation mechanism exists but is opt-in: dadaia context use <name> (CLI context.py line 222) prints export DADAIA_CONTEXT=<name> but does not execute it. The operator must run eval $(dadaia context use <name>) in their shell. When running inside Claude Code the shell environment is not persisted across tool calls, so this mechanism is effectively inert unless the operator wraps every session start.

Root cause

primary_context.json is a single global file with no session identifier, no process lock, and no TTL. Any dadaia context activate call from any process or Claude Code session overwrites it atomically. The isolation mechanism (DADAIA_CONTEXT env var) exists in the resolution chain but is never auto-exported to the Claude Code session environment — dadaia context use prints the export statement without executing it, making the isolation opt-in and effectively unusable inside an agent-driven session.

Fix options

(a) Doc + UX — make dadaia context use harder to misuse

Scope: documentation, CLI help text, and a warning message. Zero infrastructure change.

AspectDetail
What changesCLI use command prints a prominent warning when stdout is not a terminal (i.e. when called from an agent). Help text updated to emphasise eval requirement. Optionally add dadaia context use --check that prints whether DADAIA_CONTEXT is already set.
Effort~1 hour
ProsZero blast radius; zero new state; consistent with existing design.
ConsDoes not solve the bug — Claude Code sessions still cannot reliably export env vars across tool calls. Symptoms persist for concurrent sessions.
RiskLow

(b) Hook detects CLAUDE_SESSION_ID and uses session-scoped override file

Scope: ctx-inject.sh, sdd-spec-gate.sh, and one new directory under .dadaia/states/sessions/. No Python service change required for basic variant.

AspectDetail
What changesIf $CLAUDE_SESSION_ID env var is present (set by Claude Code at session start), hooks additionally check ~/.dadaia/states/sessions/$CLAUDE_SESSION_ID/primary.json before falling back to the global file. A new dadaia context pin <name> command writes the session-local override. Session directory is cleaned up on session end (or via dadaia context unpin).
Effort~4 hours (hook changes + new CLI subcommand + cleanup strategy)
ProsDirectly solves concurrent-session isolation without touching global state semantics. Backward-compatible: sessions without CLAUDE_SESSION_ID see no change. Exploits a natural session boundary already provided by the runtime.
ConsCLAUDE_SESSION_ID is not guaranteed to be stable across model updates; could become an undocumented env var. Session cleanup on crash requires a TTL or cron. Hook bash complexity increases.
RiskMedium — depends on undocumented Claude Code env var

(c) Session-local statedir — each Claude Code session owns its .dadaia/states/sessions/<id>/

Scope: Python service layer, infrastructure store, hooks, and CLI. Largest blast radius.

AspectDetail
What changesJsonPrimaryContextStore is parameterised with an optional session_id. When present, all reads and writes go to .dadaia/states/sessions/<id>/primary_context.json. The global file becomes the default for non-session (CLI) use. Container wiring passes session_id from env at startup. Hooks resolve session-local path first.
Effort~1 day (service + infra + hook + tests + migration)
ProsFully correct — every session is hermetically isolated at the data layer. Global file remains as the CLI/non-agent default. Clean architecture; testable.
ConsLarge diff across service, infra, CLI, and hooks. Session directory accumulation requires cleanup. Must verify CLAUDE_SESSION_ID availability or provide an alternative session identity mechanism (e.g., a PID-based fallback).
RiskMedium-High — touches core state layer; requires careful migration

Recommendation

Start with option (b).

Option (a) does not fix the bug — it only improves discoverability of an already-known workaround that does not work inside Claude Code sessions. Option (c) is architecturally cleanest but carries the highest blast radius for a MEDIUM-severity issue.

Option (b) addresses the root cause directly with minimal blast radius: only the two hook scripts and one new CLI subcommand change. The session-local override file pattern is additive (no migration needed), and the fallback to global state means all existing non-concurrent workflows are unaffected. If CLAUDE_SESSION_ID proves unstable, the same approach can fall back to $$ (shell PID) as the session key, which is equally effective for single-machine use.

After validating (b) in production, option (c) can be pursued as a follow-up to harden the service layer — but it is not required to close the immediate symptom.
