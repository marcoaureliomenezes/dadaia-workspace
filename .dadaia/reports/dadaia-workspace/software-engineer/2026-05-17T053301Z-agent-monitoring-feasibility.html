3. Schema real dos eventos jsonl (observado empiricamente)

ATENCAO Schema diferente do esperado no plano

O plano aprovado descrevia event.usage.{input_tokens, ...} no nivel do evento. Nos dados reais, o campo usage esta dentro de event.message: event.message.usage.{input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens}. Alem disso, o modelo esta em event.message.model, nao em event.model.

Impacto: O reader precisa navegar para event["message"]["usage"] e event["message"]["model"]. Ambos podem estar ausentes em eventos assistant sem resposta do modelo (ex: eventos sinteticos com model <synthetic>).

Identificacao de agente: o campo subagent_type descrito no plano nao foi observado em nenhum dos 7.778 eventos assistant reais. A identidade do agente vem do evento separado type=agent-name com campo agentName.

5. Reader jsonl — decisoes detalhadas

5.1 Incremental tail com offset

Decisao D1: Armazenar o offset de bytes por arquivo na tabela reader_state(file_path TEXT PK, byte_offset INTEGER, last_mtime REAL). A cada ciclo de poll, verificar os.stat(path).st_mtime; se mudou, abrir o arquivo, fazer seek(byte_offset), ler ate o fim, processar linhas completas, gravar novo offset.

Vantagem sobre re-read completo: sessoes longas (max observado: 8.9 MB, 1.478 eventos de assistant) sao processadas incrementalmente sem custo O(N) repetido.

5.2 Linha truncada (sessao em andamento)

def _safe_parse_lines(raw: str) -> tuple[list[dict], int]:
    """Retorna (eventos_validos, bytes_consumidos).

    Se a ultima linha nao termina com \n, ela esta incompleta.
    bytes_consumidos aponta para o inicio da ultima linha incompleta.
    Na proxima leitura, o seek voltara para esse ponto.
    """
    lines = raw.split("\n")
    # Ultima linha: vazia (termina em \n) ou incompleta
    if not raw.endswith("\n"):
        incomplete = lines.pop()  # descartar por ora
        bytes_back = len(incomplete.encode("utf-8"))
    else:
        bytes_back = 0
    events = []
    for line in lines:
        line = line.strip()
        if not line:
            continue
        try:
            events.append(json.loads(line))
        except json.JSONDecodeError:
            pass  # linha corrompida: pular, nao abortar
    return events, bytes_back

Arquivo corrompido (linha mal formada no meio): pular e continuar. O painel exibe os agregados que conseguiu computar; a linha perdida nao invalida a sessao inteira. Log estruturado (sem PII) registra o skip.

Disco cheio durante ingestao: a escrita no SQLite local falha com sqlite3.OperationalError. Capturar, logar, e nao atualizar o offset. Na proxima leitura o ciclo retoma do ponto anterior.

5.3 File locking — por que nao e necessario

Claude Code escreve no jsonl via append-only (O_APPEND). Em Linux, write() com O_APPEND e atomico para escritas menores que PIPE_BUF (4 KB — um evento JSON de uma linha tipicamente esta nessa faixa). O reader abre em modo read-only sem modificar o arquivo, portanto nao ha competicao de escrita. fcntl.flock seria necessario apenas se o reader tentasse truncar ou reescrever — o que nao faremos.

Estrategia de leitura segura

def read_codex_threads(db_path: Path) -> list[dict]:
    """Le threads do Codex em modo read-only. Degrada graciosamente."""
    uri = f"file:{db_path}?mode=ro"
    try:
        conn = sqlite3.connect(uri, uri=True, timeout=5.0)
        conn.row_factory = sqlite3.Row
        cur = conn.cursor()
        # Colunas que sabemos existir na versao observada; novas colunas = ignoradas
        cur.execute("""
            SELECT id, model_provider, model, tokens_used,
                   created_at, cwd, title, agent_nickname, git_branch
            FROM threads
            WHERE has_user_event = 1
        """)
        rows = [dict(r) for r in cur.fetchall()]
        conn.close()
        return rows
    except sqlite3.OperationalError as exc:
        # Schema mudou ou coluna ausente: log + retornar lista vazia
        _log_warning(f"codex_reader: schema mismatch or lock: {exc}")
        return []

WAL mode no Codex permite multiplos readers concorrentes sem bloquear o writer. O timeout de 5s previne que o panel trave se o Codex estiver em transacao longa. Se o Codex nao usar WAL (improvavel), o pior caso e um OperationalError: database is locked que e tratado graciosamente.

Limitacao de custo para Codex

tokens_used e um inteiro agregado sem separacao in/out/cache. Para Codex, reportar apenas tokens totais, sem estimativa de custo em USD. Ou, como estimativa grosseira, aplicar o preco medio de input do modelo como proxy. Esta limitacao deve ser documentada no UI ("custo estimado, sem breakdown de tokens").

7. Schema migration — estrategia

Decisao D5: PRAGMA user_version como versao corrente do schema. Ao iniciar o TelemetryService, executar uma sequencia de migracoes numeradas: 
MIGRATIONS: dict[int, str] = {
    1: """
        CREATE TABLE IF NOT EXISTS reader_state (
            file_path TEXT PRIMARY KEY,
            byte_offset INTEGER NOT NULL DEFAULT 0,
            last_mtime  REAL NOT NULL DEFAULT 0.0
        );
    """,
    2: """
        CREATE TABLE IF NOT EXISTS sessions (
            session_id   TEXT PRIMARY KEY,
            agent_name   TEXT,
            ai_title     TEXT,
            entrypoint   TEXT,
            cwd          TEXT,
            git_branch   TEXT,
            first_event  TEXT,  -- ISO timestamp
            last_event   TEXT,
            provider     TEXT DEFAULT 'claude-code'
        );
    """,
    3: """
        CREATE TABLE IF NOT EXISTS events (
            event_id         TEXT PRIMARY KEY,  -- sessionId:uuid
            session_id       TEXT NOT NULL,
            timestamp        TEXT,
            model            TEXT,
            input_tokens     INTEGER DEFAULT 0,
            output_tokens    INTEGER DEFAULT 0,
            cache_creation   INTEGER DEFAULT 0,
            cache_read       INTEGER DEFAULT 0,
            cost_usd         REAL,              -- NULL se modelo nao na tabela
            FOREIGN KEY (session_id) REFERENCES sessions(session_id)
        );
    """,
    4: """
        CREATE INDEX IF NOT EXISTS idx_events_session ON events(session_id);
        CREATE INDEX IF NOT EXISTS idx_sessions_agent ON sessions(agent_name);
        CREATE INDEX IF NOT EXISTS idx_sessions_first ON sessions(first_event);
    """,
    5: """
        CREATE TABLE IF NOT EXISTS codex_threads (
            thread_id    TEXT PRIMARY KEY,
            model        TEXT,
            provider     TEXT DEFAULT 'codex',
            tokens_total INTEGER DEFAULT 0,
            cwd          TEXT,
            title        TEXT,
            created_at   TEXT
        );
    """,
}

def apply_migrations(conn: sqlite3.Connection) -> None:
    current = conn.execute("PRAGMA user_version").fetchone()[0]
    for version, sql in sorted(MIGRATIONS.items()):
        if version > current:
            conn.executescript(sql)
            conn.execute(f"PRAGMA user_version = {version}")
            conn.commit()

Se o schema crescer alem de 10 versoes, reavaliar se uma lib externa como alembic (ou yoyo-migrations) compensa. Ate la, stdlib e suficiente. Como a DB e derivada (pode ser dropada e recriada do zero via re-ingestao dos jsonl), o risco de migracoes quebradas e baixo: pior caso = drop + recreate + reingest.

8. Estrategia de testes

  • Fixtures jsonl sinteticas — criar arquivos tmp_path/session_VALID.jsonl, session_TRUNCATED.jsonl, session_MALFORMED_MID.jsonl, session_EMPTY.jsonl. Todos gerados in-memory no fixture, sem tocar o filesystem real.
  • SQLite in-memory para testes de schema: sqlite3.connect(":memory:"). Nao depende do arquivo do operador.
  • Pricing unit tests: testar compute_cost(usage, model, when) com:
    • modelo conhecido no periodo correto
    • modelo conhecido em periodo anterior (preco historico)
    • modelo desconhecido (retorna None)
    • usage todos zeros (retorna 0.0)
  • Reader tests: _safe_parse_lines testada com string truncada, string com linha mal formada no meio, string vazia, string com linhas vazias entre eventos validos.
  • Offset tests: simular dois ciclos de poll onde o arquivo cresce entre ciclos; verificar que o segundo ciclo nao reprocessa eventos do primeiro.
  • Idempotencia: ingerir o mesmo jsonl duas vezes; verificar que SELECT COUNT(*) FROM events produz o mesmo resultado nas duas corridas.
  • Codex reader: testar com SQLite in-memory com schema parcial (coluna faltando) e verificar que retorna lista vazia sem excecao.
  • Migration tests: aplicar migracoes em DB in-memory; verificar PRAGMA user_version apos cada etapa; aplicar novamente (idempotente).
  • Sem network, sem filesystem real fora de tmp_path (pytest fixture), sem subprocess.

Conclusao

A viabilidade tecnica do reader e confirmada com stdlib Python only. Os dados reais sao mais complexos do que o plano descrevia (usage em event.message.usage, sem subagent_type, identidade via agent-name event), mas todos os casos sao cobertos com parsing defensivo e nenhuma dependencia nova. O unico risco de performance em horizonte de 6 meses (target 80 MB SQLite, query <50ms) e mitigado pelos indices propostos. A estrategia de ingestao incremental com offset garante que sessoes em andamento nao causem re-processamento desnecessario.
