# Contributing to dadaia-workspace

Welcome, and thank you for your interest in contributing. This guide explains how the
project works, what to expect from the contribution process, and how to get your changes
reviewed and merged.

---

## Fork-only model

This repository uses a **fork-only contribution model**. External contributors cannot
push branches directly to the origin repository or merge pull requests themselves.

To contribute:

1. Fork the repository to your own GitHub account.
2. Clone your fork locally and create a feature branch.
3. Make your changes and push them to your fork.
4. Open a Pull Request from your fork's branch to `main` in this repository.
5. A CODEOWNERS review will be requested automatically. The maintainer reviews and merges.

Contributors do not have write access to the upstream remote. Branch protection on `main`
enforces this rule even for the repository owner.

## How the `specs/` directory works (SDD lifecycle)

This project is developed using **Spec-Driven Development (SDD)**. The `specs/` directory
is the single source of truth for what the product *is* and what is *changing* in each
release.

### Key directories

| Path | Purpose |
|------|---------|
| `specs/constitution.md` | Absolute laws of the product — read first |
| `specs/memory/` | Atomic HTML snapshots of the current product state |
| `specs/releases/<release-id>/` | One directory per release; contains SPEC, PLAN, TASKS, CLOSURE |
| `specs/backlog/` | Informal ideas and formal release candidates |
| `specs/_archive/` | Completed and archived releases (read-only history) |

### Release lifecycle

Every change ships inside a named release. Each release goes through this status ladder:

```
Draft  →  Em revisão  →  Aprovado
```

A release directory contains up to four files:

- `SPEC.md` — what is changing and why (must reach `Aprovado` before implementation)
- `PLAN.md` — how the implementation will be structured (must reach `Aprovado`)
- `TASKS.md` — the ordered checklist of atomic tasks
- `CLOSURE.md` — post-release summary, validations, and memory updates

### Task markers

Tasks in `TASKS.md` use three markers:

| Marker | Meaning |
|--------|---------|
| `[ ]` | Open — not yet started |
| `[-]` | In progress — an agent or contributor has reserved this task |
| `[x]` | Done — implemented, verified, and committed |

**Rule:** at most one `[-]` per contributor at a time unless the TASKS.md explicitly
declares parallel-safe tasks with disjoint write sets.

If you are implementing a task, flip `[ ]` to `[-]` in a commit before starting work,
and flip `[-]` to `[x]` in your final commit for that task.

## Generated directories — never commit these

The following directories and files are **generated automatically** by the
`dadaia public stage` and `dadaia public install` commands. They are runtime projections
of the library's canonical assets and must never be committed to version control.

```
.claude/           # Claude Code agent context (generated by dadaia public install)
.agents/           # OpenCode agent context (generated by dadaia public install)
.codex/            # Codex agent context (generated by dadaia public install)
.opencode/         # opencode config (generated by dadaia public install)
.dadaia/agentic/   # Staging area (generated by dadaia public stage)
.dadaia/scripts/   # Deployed hook scripts (generated by dadaia public install)
.dadaia/states/    # Runtime state (instance-specific)
.dadaia/tmp/       # Ephemeral temp files
```

All of these paths are covered by `.gitignore`. If you ever see them appear in
`git status` as untracked or modified, do not add them to a commit. Run
`dadaia public stage && dadaia public install` to regenerate them from the source.

**Exception:** `opencode.json` at the repository root is intentionally tracked. It is a
starter template for consumers installing this library and should remain in version
control.

### About `AGENTS.md`

The `AGENTS.md` file at the repository root is also lib-originated. It is the workspace
agent-rules document consumed by AI coding assistants (Claude Code, OpenCode, etc.) and
is propagated by `dadaia public install` from the canonical source at
`dadaia_workspace/public/data/AGENTS.md`. It is not a human contribution guide.

If you need to add a workspace rule, scope it to a repo-local rule file under
`repos/<your-repo>/.claude/rules/<your-rule>.md`. Do not edit `AGENTS.md` in place — it
will be overwritten on the next `dadaia public install` run.

## Adding new agent rules

Agent rules in `dadaia_workspace/public/rules/` and
`dadaia_workspace/public/agents/` are **canonical global assets** consumed by every
workspace that installs this library. They must remain generic and must not contain
references to any specific deployment topology, container names, or file paths of a
particular consumer.

If you need a rule that applies only to your fork or a specific context, add it as a
**repo-local rule** in your own repository overlay:

```
repos/<your-repo>/.claude/rules/<your-rule>.md
```

Do not add consumer-specific rules to the canonical `public/` assets. Doing so corrupts
every other consumer of the library.

## Running the test suite

This project uses [Poetry](https://python-poetry.org/) for dependency management.

**Prerequisites:**
- Python 3.12+
- Poetry installed (`pip install poetry` or via the official installer)

**Run the test suite:**

```bash
cd repos/dadaia-workspace
poetry install
poetry run pytest
```

All tests must pass before you open a Pull Request. Do not rely on CI as your first
feedback loop — run `poetry run pytest` locally first.

**Note on Node.js:** Node.js is only required for the Playwright end-to-end tests under
`tests/e2e/`. If you are not working on E2E tests, Node.js is not needed.

## Commit conventions

This project follows [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short description>

Examples:
feat(public): add new agent skill for X
fix(cli): correct path resolution in dadaia context show
chore(repo): update .gitignore entries
docs: add CONTRIBUTING.md
test: add unit test for _is_self_repo guard
```

## Questions and discussions

For questions, open a GitHub Discussion or an Issue. For bugs, open an Issue with
reproduction steps. For feature proposals, check `specs/backlog/candidates.md` first —
if your idea is already there, reference it in the Issue.
